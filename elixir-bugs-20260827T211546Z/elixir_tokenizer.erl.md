## Bugfixes

#### `CSCAN-elixir_tokenizer-atom-length-byte-vs-codepoint`
- **Finding ID** — `CSCAN-elixir_tokenizer-atom-length-byte-vs-codepoint`
- **Severity** — Low
- **Confidence** — **high** (upgraded from medium; mechanism now executed, see Evidence)
- **Location** — `elixir_tokenizer.erl:1077-1079`, `unsafe_to_atom/4` (first clause)
- **Class** — Off-by-one / wrong arithmetic (unit mismatch: bytes vs code points)
- **User-visible outcome** — A quoted atom made of multibyte characters that is at/under the 255-**character** Erlang atom limit but over 255 UTF-8 **bytes** (e.g. `:"ää…"` with 128 two-byte characters = 256 bytes, 128 characters) is rejected at tokenization with `"atom length must be less than system limit: "`, even though `binary_to_atom/2` creates it successfully and the sibling charlist path (`length(Part) > 255`, line 1079) accepts it. The caller observes a valid ≤255-character atom failing to compile with a spurious "system limit" error.
- **Reproduction** — `Code.string_to_quoted(~s|:"| <> String.duplicate("ä", 128) <> ~s|"|)`. The `:"..."` path (`elixir_tokenizer.erl:551-553`) unescapes the parts to a single binary and calls `unsafe_to_atom(Part, …)` with `is_binary(Part)` (line 552 guard). For 128×`ä` the binary is 256 bytes / 128 code points, so the guard `is_binary(Part) andalso byte_size(Part) > 255` (line 1078) fires and returns the "system limit" error, while the actual constructor `binary_to_atom(Binary, utf8)` (line 1125) would succeed.
- **Suggested fix** — Count code points in the binary guard, e.g. replace `is_binary(Part) andalso byte_size(Part) > 255` with a code-point count (`length(unicode:characters_to_list(Part)) > 255`), optionally gating the cheap `byte_size > 255` as a fast pre-filter and confirming the true character count before erroring — keeping it symmetric with the list branch on line 1079.
- **Risk of fix** — Atoms in the 256-byte…255-character window that currently error would be accepted (as they already are via the charlist path). No currently-accepted input changes behaviour. One extra UTF-8 walk on the >255-byte error path only.
- **Evidence** —
  - Read `elixir_tokenizer.erl:1077-1136`: the two guards differ in unit (`byte_size` line 1078 vs `length` line 1079); the constructor is `binary_to_atom(Binary, utf8)` (line 1125).
  - Read `elixir_tokenizer.erl:551-553`: confirms a **binary** `Part` reaches `unsafe_to_atom/4`, so the buggy binary guard is on the live `:"..."` path.
  - **Executed** (`erl`, OTP 17.0.2), binaries built from raw code points to avoid double-encoding:
    - 128×U+00E4 → **256 bytes / 128 chars** → `binary_to_atom` **succeeds** (`{ok,128}`).
    - 200×U+00E4 → 400 bytes / 200 chars → **succeeds** (`{ok,200}`).
    - 255×U+00E4 → 510 bytes / 255 chars → **succeeds** (limit is inclusive at 255).
    - 256×U+00E4 → 256 chars → `system_limit` (fails).\
    This proves the Erlang atom limit is **255 code points, not bytes**, so the `byte_size > 255` guard over-rejects every valid multibyte atom in the 256-byte…255-char window.
