# Cluster cross-file findings

#### `CSCAN-cluster-string-replace-forwards-regex-template-crash`

- **Finding ID:** `CSCAN-cluster-string-replace-forwards-regex-template-crash`
- **Severity:** Low
- **Confidence:** high
- **Files involved:**
  - `/Users/lukas/code/claude-scanner/elixir/lib/elixir/lib/string.ex` — `replace/4` docs advertising the `\N`/`\g{N}` template syntax (1640–1649); `replace/4` public guard (1683–1689); `replace_guarded/4` forwarding to Regex (1691–1693, sink call at **1692**)
  - `/Users/lukas/code/claude-scanner/elixir/lib/elixir/lib/regex.ex` — `replace/4` (841–858); crashing template parser `precompile_replacement/1` `\g{` clause (**867–870**) and `pick_int/1` (891–898)
- **Finding shape:** Taint across files — attacker-controlled data enters in file A (`String.replace/4`) and flows into a crashing sink in file B (`Regex.replace/4`'s `precompile_replacement/1`) with no re-validation at the `String` boundary.
- **Evidence:**
  - `string.ex:1684-1692`: `String.replace/4` accepts any binary `replacement` (`is_binary(replacement) or is_function(replacement, 1)`) and, when the pattern is a Regex, forwards it verbatim: `defp replace_guarded(subject, %{__struct__: Regex} = regex, replacement, options), do: Regex.replace(regex, subject, replacement, options)`. There is **no validation of the replacement template** on the `String` side.
  - `string.ex:1640-1649`: `String.replace/4`'s own documentation explicitly tells callers to put `\N` / `\g{N}` capture references in the `replacement` string ("one can give `\N` or `\g{N}` in the `replacement` string to access a specific capture") — i.e. it actively invites template strings through this exact path.
  - `regex.ex:867-870`: `precompile_replacement(<<?\\, ?g, ?{, rest::binary>>)` does `{ns, <<?}, rest::binary>>} = pick_int(rest)` then `List.to_integer(ns)`. For `"\\g{}"`, `pick_int("}")` returns `{[], "}"}`, so `List.to_integer([])` raises `ArgumentError`; for `"\\g{x}"`, `pick_int("x}")` returns `{[], "x}"}`, so the tuple/binary match on line 868 fails with `MatchError`. Traced by code-reading; the crash itself is verified-by-execution in the per-file `regex.ex` report (`CSCAN-regex-replace-malformed-backref-crash`). Net effect: `String.replace(subject, ~r/./, "\\g{}")` and `String.replace(subject, ~r/./, "\\g{x}")` crash the calling process with an internal `ArgumentError`/`MatchError` (the latter leaks an internal intermediate value and defeats a caller's `rescue ArgumentError`).
- **What the per-file pass missed:** The `regex.ex` reviewer found the parser crash but scoped its trust boundary to direct `Regex.replace/4` callers; the `string.ex` reviewer treated `Regex.replace` as an opaque forward and did not fuzz the regex replacement grammar (its own replace fuzzing covered only the string/list/compiled-pattern branches). Only looking at both files together reveals that `String.replace/4` — the far more idiomatic API, whose documentation advertises `\g{N}` — is a second, unguarded entry point to the same crash, so a service doing `String.replace(user_text, regex, user_template)` is exposed even if it never calls `Regex.replace/4`.
- **Suggested fix:** Shared with `CSCAN-regex-replace-malformed-backref-crash` — make the `\g{` clause in `regex.ex:867-870` total (guard `pick_int` for a non-empty digit run followed by `}`, and raise one descriptive `ArgumentError` — or treat a malformed `\g{…}` as a literal, mirroring the bare-`\g` catch-all). Fixing it in `regex.ex` closes both the `Regex.replace/4` and `String.replace/4` entry points; no separate change to `string.ex` is required once the parser is total.
