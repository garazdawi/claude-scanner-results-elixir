# Prompts used for this scan

This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert Elixir programmer performing a focused bugfix review of a single source file. Review only the file at the path below.

${FILE}

Your sole objective is to find real, triggerable bugs reachable through the file's documented public API. Do not modify any files. Do not run tools that write to the tree. Output only the markdown report described at the end.

## Scope — what counts

In scope: defects reachable through documented public API (public/exported functions, documented behaviours and callbacks, `@doc`'d entry points). Untrusted data reaching vulnerable code through a documented public API is fully in scope even when exploitation requires an attacker — parser/decoder bugs on network input, file-format handling, and any code path callable from a documented entry point all count.

Out of scope — ignore findings only reachable through misuse of internal interfaces:
- Bugs reachable only by calling private / non-exported / non-public-API functions, by sending crafted messages to undocumented internal processes, or by depending on implementation details that are not part of the documented public API.
- Bugs that require the caller to pass arguments violating the function's documented `@spec` / contract / header declaration. Elixir does not enforce these at runtime, so they are uninteresting.

A crash is not automatically a bug. Raising on invalid input is often the contract. A finding is a crash where the documented contract promises an error tuple, a crash on valid input, or a crash whose message tells the caller nothing about what to fix.

## Phase 1 — inventory (do not skip)

Before judging anything, enumerate candidate defects. The classes below are a coverage floor, not a ceiling — use them to hunt thoroughly, not as the limit of what counts. A bug outside the list is first-class; put it in `Unclassified`. Force-fitting a finding into a class that doesn't apply is worse than declaring it `Unclassified`. Enumerate first, judge second.

- **Missing clause / non-total function** — a function head or `case` handling N shapes but not the (N+1)th a caller actually produces. Surfaces as `FunctionClauseError` or `CaseClauseError`, often on benign input. `with/1` is a common site: an unmatched pattern falls to `else`, and an absent `else` returns the unmatched value itself instead of raising — a silent wrong return.
- **Operator / precedence** — `and`/`&&` and `or`/`||` are not interchangeable (`and` requires a boolean; `&&` treats `nil`/`false` as falsy); `|>` binds tighter than expected; `not` vs `!`; `==` vs `===`; a guard satisfied by every input or by none.
- **Truthiness confusion** — `nil` and `false` are falsy, everything else truthy, so a function returning `{:ok, false}` or `nil` for "absent" behaves differently under `if` than under a pattern match. Check the caller distinguishes "returned false" from "returned nothing".
- **Pattern match on the wrong shape** — matching `{:ok, x}` where the callee returns `:ok`, matching a map with more keys than the pattern assumes, matching a struct by its map shape and accepting a different struct.
- **State / accumulator threading** — stale binding after a rebind, unchanged accumulator into a recursive call, wrong tuple element returned, a field dropped across a refactor. `Enum.reduce` bodies are the usual site.
- **Off-by-one / wrong arithmetic** — `String.length` (graphemes) where `byte_size` was meant or vice versa; `String.slice` ranges; mixing milliseconds and native time units; `div` where `rem` was intended.
- **Binary vs charlist vs string** — `String` functions on a charlist, `Enum` on a binary, `to_string/1` on something whose `String.Chars` differs from the author's assumption, or a function accepting both and behaving differently down each branch.
- **Unicode correctness** — treating a binary as characters: `String.length` counts graphemes, `byte_size` counts bytes, `String.at/2` is O(n); slicing a binary at a byte offset can split a codepoint; case operations are locale-/mode-sensitive (`String.downcase(s, :greek)`).
- **Contract violation** — a function returning a shape its `@spec`, `@doc`, or doctest does not describe; a callback implementation whose return does not match the behaviour's `@callback`; a bang function returning `{:error, _}` instead of raising, or a non-bang that raises.
- **Protocol and behaviour errors** — a `defimpl` for the wrong type, a protocol call on a type with no implementation and no fallback, an `@impl` on a non-callback, a missing optional-callback guard.
- **Macro and compile-time errors** — hygiene violations that capture or leak a variable, `unquote` at the wrong quoting depth, a macro evaluating its arguments more than once (double side effects), AST built with wrong metadata so errors point at the wrong line.
- **Process and message errors** — a `receive`/`handle_info` without a catch-all leaving messages in the mailbox forever; a monitor or timer never cleaned up; a `GenServer.call` from within the same process; a reply sent twice or not at all; linking where monitoring was meant.
- **Timeout and lifetime** — an infinite timeout where the caller expects to recover, a `Task.await` shorter than the work, a supervisor restart strategy that cannot converge.
- **Resource leak** — files, ports, ETS tables, or processes created on a path that can exit before releasing them.
- **Error-handling asymmetry** — `rescue` catching `Exception` but not `throw`/`exit`, `try/after` swallowing the original error, an error tuple discarded by `_ = ...` or by an unmatched `with`.
- **Dead / unreachable code** — a clause that can never match given earlier clauses, a guard always true, a branch whose condition contradicts an earlier match.
- **Documentation mismatch** — the `@doc` or a doctest describes behaviour the code does not have. A doctest that would fail if run is a bug in one of the two; say which.
- **Unclassified** — anything wrong that fits none of the above.

## Phase 2 — per-finding, in order

For each candidate: (1) state the input or call sequence that triggers it. (2) Say what happens instead of what should happen — the actual error, wrong value, or hang. (3) **Reproduce it by running.** The sandbox has `elixir`, `iex`, `mix`, and `erl` BUILT FROM THE SOURCE UNDER REVIEW, so a behavioural claim is settled in seconds: write the smallest script that drives it and run it (`elixir -e '...'`), observe, and cite the output. Doctest and `@spec` claims can be checked the same way. Fall back to a reasoned sketch only when you genuinely cannot run it — a claim you could have tested but only reasoned about is `asserted`, not `verified`. (4) Rate Critical / High / Medium / Low by what it costs a caller who hits it.

Additional obligations:
- Documentation is a contract. `@doc` and doctests are executable and published; where code and documentation disagree, say which one you believe is wrong and why, rather than assuming the code is right. A doctest that cannot currently pass is a finding.
- `@spec` disagreeing with the implementation is a finding even when no runtime failure follows, because Dialyzer consumes it and the error propagates into every caller's analysis.

## Output format

Produce a concise markdown report and nothing else — no preamble, no file modifications. The report has, in order:

1. A `## Summary` section: one sentence.
2. A `## Bugfixes` section: the findings. Write `No findings` if nothing meaningful is found.
3. A `## Risks / caveats` section.

Include no sections other than these three.

Each finding begins with a level-4 heading containing only its Finding ID in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-parser-merge-token-quadratic`, not `CSCAN-parser-finding-1`), derived from what the bug is so a re-scan produces the same id for the same bug. Under 40 characters; no line numbers or version numbers.

Immediately below the heading, these fields on separate lines, in order:

- **Finding ID** — as above.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class, or `Unclassified (<short label>)`.
- **Issue** — what is wrong: the triggering input/call and what happens instead of what should happen.
- **Suggested fix** — the smallest change that removes the defect.
- **Impact / threat** — what it costs a caller who hits it, and the threat where untrusted data reaches the code through the public API.
- **Evidence** — `verified` (quote the command and output) when you ran it, `asserted` when you reasoned only. A claim you could have tested but did not is `asserted`.

Findings you considered and rejected go under a `### Ruled out` heading at the end of the Bugfixes section, one bullet each with the reason; no Finding ID for those.

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof. A ruled-out entry whose basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. Every claim of absence is a claim about a search space and stands only when the space and the search are named — name where you looked, name the upstream mechanism and its default for a parity claim, and do not credit a mitigation ("requires authentication") the threat model does not grant when the entry point accepts untrusted input from the network.

Write `No findings` under Bugfixes if nothing meaningful is found. Output only the markdown report.
````
