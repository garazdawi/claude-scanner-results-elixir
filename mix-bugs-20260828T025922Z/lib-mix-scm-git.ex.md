### Ruled out

- **`parse_version`/version-tuple size comparison** — Erlang term ordering compares tuples by arity first, so a 2-component version (e.g. `{2,39}`) compares as *less than* the 3-component minimums like `{1,7,1}`, which would wrongly disable `--progress`/depth/sparse support. *Verified* the comparison anomaly (`{1,7,1} <= {2,39}` → `false`). Ruled out: reaching it requires the local `git` binary to report a 2-part version string with no patch level, which real git never emits; the input is local-tool output in a well-behaved environment, not documented-API data.
- **`format_lock/1` with a non-binary `lock_rev`** — `String.slice(lock_rev, 0, 7)` would raise if the third lock-tuple element weren't a binary. Ruled out: the lock tuple is generated by `get_lock/1` (always a binary rev); supplying a non-binary requires a hand-edited `mix.lock` that violates the format contract, and reading such a lock is already arbitrary-code-execution territory.
- **`redact_uri/1` does not redact scp-style URLs** (`git@github.com:foo/bar.git`) — *verified* it returns the URL unchanged. Ruled out as a bug: `URI.parse` yields `userinfo: nil` for scp syntax and these URLs carry no password; behaviour matches upstream design, and it is a display cosmetic, not a defect in program behaviour.
- **`equal?/2` key-order sensitivity via `Keyword.take`** — considered whether semantically-equal option sets in different key orders compare unequal. Both sides pass through the same `get_lock_opts` ordering, and lock opts are stored/compared consistently, so no asymmetry; matches upstream.
