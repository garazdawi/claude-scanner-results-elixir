## Summary
The `Code` module's code-execution and code-loading APIs behave as documented (with explicit "don't use with untrusted input" warnings). The one meaningful finding stands: `Code.fetch_docs/1` — a documented public API that reads docs from an arbitrary `.beam`/`.chunk` file — deserializes attacker-controlled bytes with an unbounded, non-`:safe` `:erlang.binary_to_term/1`, yielding a verified memory- and atom-exhaustion DoS.

The first pass carried one substantive hedge: the claim that the `string_to_quoted*` / `format_*` parse forwarders push all input-sanitization responsibility into "other files" (the tokenizer) and therefore introduce no code.ex-local risk. I resolved that hedge by reading the callgraph neighbour `src/elixir.erl` (the module `code.ex` forwards into) rather than assuming it. Result: the forwarders are pure pass-throughs into `elixir_tokenizer:tokenize/4`, the designated sanitizer, so no code.ex-local finding arises — see the upgraded caveat below. No new findings resulted.

## Security

#### `CSCAN-code-fetch-docs-unsafe-binary-to-term`
- **Finding ID:** `CSCAN-code-fetch-docs-unsafe-binary-to-term`
- **Severity:** Medium
- **Confidence:** high
- **Location:** `lib/elixir/lib/code.ex:2383`, `load_docs_chunk/1` (reached from `fetch_docs_from_beam/1` at line 2359 and `fetch_docs_from_chunk/1` at line 2375, via the public `fetch_docs/1`, path clause at lines 2340–2342).
- **Class:** Deserialisation (CWE-502), with the concrete impact being Resource consumption (CWE-770).
- **Issue:** `load_docs_chunk/1` decodes the `Docs` chunk of a BEAM/`.chunk` file with `:erlang.binary_to_term(bin)` and no `[:safe]` option and no size bound. `Code.fetch_docs/1` is documented to accept an arbitrary path ("When given a path to a `.beam` file, it will load the docs directly from that file"), so the bytes handed to `binary_to_term` are fully attacker-controlled whenever the file is untrusted. The public path clause `fetch_docs(path) when is_binary(path)` at line 2340 flows straight to `fetch_docs_from_beam/1` → `:beam_lib.chunks` → `load_docs_chunk/1`, with no interposed validation. Non-`:safe` `binary_to_term` creates new atoms (which are never garbage-collected) and will decompress the compressed external-term format, and there is no ceiling on the decoded term size.
- **Impact / threat:** A single `Code.fetch_docs/1` call on a ~281 KB crafted `.beam` allocated 200 MB (a ~1000× compression bomb → OOM the host process/VM); a ~2.3 MB crafted `.beam` injected 100,000 permanent atoms in one call (default limit 1,048,576, never reclaimed → a handful of files permanently degrades then crashes the VM). The trust boundary crossed is an untrusted `.beam`/`.chunk` file — e.g. a docs-hosting/indexing service that extracts documentation from uploaded packages, or doc tooling / language servers reading a dependency's compiled artifacts. No code execution results (that is not what `binary_to_term` does), but it is an unauthenticated denial of service.
- **Evidence:** `verified` (executed in the first pass; the underlying external-term-format semantics — non-`:safe` atom creation and transparent decompression of the compressed term format — are version-independent, so the reproduction remains valid).
  - Atom-injection primitive: `:erlang.binary_to_term(bytes,[:safe])` → `{:raised, ArgumentError}` (refuses), plain `:erlang.binary_to_term(bytes)` → created `:cscan_novel_atom_1577` (`exists after non-safe? true`).
  - Compression bomb: `term_to_binary(:binary.copy("A", 200_000_000), [{:compressed, 9}])` = `194423` bytes on disk → `binary_to_term` decoded a `200000000`-byte term, `VM total memory delta: 200 MB`; `:safe` decodes it too.
  - End-to-end bomb through public API: forged the `Docs` chunk of the real `Elixir.String.beam` (via `:beam_lib.all_chunks`/`build_module`) → `Code.fetch_docs("/tmp/evil_real.beam")` → result was a `200000000`-byte binary, `VM memory delta from ONE fetch_docs call: 200 MB` (evil beam only `281632` bytes).
  - End-to-end atom exhaustion through public API: `Docs` chunk encoded (as raw external-term bytes, so the builder never created the atoms) as a list of 100,000 novel atoms → `Code.fetch_docs("/tmp/evil_atoms2.beam")` → `NEW atoms created by ONE fetch_docs call: 100000`, `atom_count 18689 → 118689`, `atom table limit: 1048576`.
  - Fix-viability check: `:safe` is not a drop-in fix — decoding `URI`'s *legitimate* `Docs` chunk under `[:safe]` returned `{:safe_rejected, ArgumentError, ...}` because docs chunks legitimately reference atoms not resident when reading docs of an unloaded module.
- **Suggested fix:** Do not decode untrusted docs chunks with an unbounded, unsafe `binary_to_term/1`. `[:safe]` alone is insufficient (it does not bound allocation, so it leaves the compression bomb, and it breaks legitimate unloaded-module docs — verified above). Decode within a bounded context instead: run the `binary_to_term` in a short-lived process spawned with a `max_heap_size` limit (so a bomb kills only that transient process, not the VM) and/or reject payloads whose declared uncompressed size (readable from the compressed-term header) exceeds a sane threshold, returning `{:error, {:invalid_chunk, _}}` on breach. At minimum, document in `fetch_docs/1` that the path form must only be used on trusted `.beam`/`.chunk` files.

## Risks / caveats
- **`string_to_quoted*` / `string_to_quoted_with_comments` / `format_string!` / `format_file!` on untrusted source — Upgraded from hedged assumption in first pass.** The first pass *assumed*, without reading them, that these forward to a tokenizer that owns all input sanitization. I verified this by reading the callgraph neighbour `src/elixir.erl`:
  - `Code.string_to_quoted/2` (code.ex:1364–1369), `string_to_quoted!/2` (1383–1388), and `string_to_quoted_with_comments/2` (1438–1453) all do nothing but marshal `file`/`line`/`column`/`opts` and call `:elixir.string_to_quoted(to_charlist(string), …)`. code.ex performs no byte-level handling of its own.
  - `:elixir.string_to_quoted/5` (elixir.erl:500–516) → `string_to_tokens/5` (456–462) → `elixir_tokenizer:tokenize/4` (457), then `tokens_to_quoted/3` → `elixir_parser:parse/1`. This matches the standing cross-file invariant that "`elixir_tokenizer` is the sole sanitiser of raw bytes" (bidi/break rejection, UTF-8 validation, escape handling). No sanitization is skipped or duplicated by the code.ex forwarder, and the forwarder adds no new sink.
  - Consequence: the two residual concerns are correctly attributed to *other files that are themselves separate review targets*, not to code.ex — (a) tokenizer atom creation when `existing_atoms_only: false` (documented default; opt-outs `:existing_atoms_only`/`:static_atoms_encoder` at code.ex:1289–1338) happens inside `elixir_tokenizer`, and (b) any quadratic/deep-nesting DoS in tokenization/parsing lives in `elixir_tokenizer.erl` / `elixir_parser.yrl`. These are not code.ex findings. I did not re-audit those tokenizer/parser internals here (they are reviewed on their own files); I verified only that code.ex is a faithful pass-through into them.
- The `fetch_docs` finding was fully reproduced end-to-end against binaries built from the source under review (first pass, Elixir 1.21.0-dev). Severity is scoped to denial of service; I found no path from this file's public API to code execution beyond the already-documented `eval_*`/`compile_*` functions.
- I did not attempt to enumerate every consumer of `Code.fetch_docs/1` in the wider ecosystem; the finding rests on the documented API contract (arbitrary `.beam` path accepted, code.ex:2340–2342) rather than on a specific downstream caller. This does not weaken the finding — the public contract alone establishes the untrusted-input reachability.
