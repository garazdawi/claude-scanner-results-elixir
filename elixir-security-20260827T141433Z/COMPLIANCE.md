## Violations

#### `CSCAN-elixir-rfc-directional_formatting_not_prohibited`
- **Finding ID:** `CSCAN-elixir-rfc-directional_formatting_not_prohibited`
- **Severity:** Low
- **Clause:** DIRECTIONAL_FORMATTING_NOT_PROHIBITED — Do not outright prohibit directional formatting characters (they are needed for correct bidi display); prefer warning when their effect spans atoms. (cites: Unicode UTS #55 §5.1.6) (quote: "Implementations should not prohibit the use of the directional formatting characters") [SHOULD NOT]
- **RFC:** 
- **Location:** elixir_interpolation.erl:95-102 (strings) and elixir_tokenizer.erl:1357-1358 (comments); rejection set at elixir_tokenizer.hrl:27-35
- **Evidence:** `?bidi(C)` matches all nine directional formatting characters (202A/B/C/D/E, 2066/7/8/9); every raw occurrence in a string (`extract_char`, interpolation.erl:95 → `{error,...}`) or comment (`tokenize_comment`, tokenizer.erl:1357 → `{error,...}`) is a hard tokenizer error with message "invalid bidirectional formatting character…, use it in its escaped \uXXXX form instead". A folder-wide grep for `directional`/`202x`/`206x`/warn found no warn-based path — the only handling is unconditional rejection.
- **Suggested fix:** Don't hard-reject raw directional formatting characters; per UTS #55 §5.1.6, permit them and instead emit a warning when a character's effect is unterminated/spans a token (atom) or comment boundary — i.e. downgrade the `{error,...}` branches to a scoped warning for balanced/contained usage.

This folder is the tokenizer, so it owns the source-code handling of directional formatting characters that UTS #55 §5.1.6 governs — the clause applies. I traced all bidi handling: the `?bidi/1` macro (tokenizer.hrl:27-35) enumerates exactly the nine directional formatting characters, and both raw-source sites that could contain them — string extraction (elixir_interpolation.erl:95-102) and comment scanning (elixir_tokenizer.erl:1357-1358) — return an immediate `{error,...}` on the very first such character, with no exception for balanced/terminated isolates or embeddings and no configuration to allow them. A grep across the folder for any warning-based or "spans atoms" handling returned nothing; the `WarnMsg`/`prepend_warning` hits are unrelated. This is precisely the outright prohibition the SHOULD NOT clause counsels against ("Implementations should not prohibit the use of the directional formatting characters… they are needed to display right-to-left text correctly"), and the recommended alternative (warn when the effect spans atoms) is not implemented. The deviation is a deliberate, defensible choice to prioritize the conflicting Trojan-Source/UAX #9 rejection requirement over UTS #55 §5.1.6 flexibility, and it offers an escape (`\uXXXX`) so the codepoint can still reach runtime data — but forcing escaping still prohibits the raw characters in source, so the SHOULD NOT is not satisfied. Severity is Low: no attacker uplift (the behavior is strictly more restrictive/safer), the only cost is legitimate RTL source literals/comments cannot use raw controls.
