## Violations

#### `CSCAN-elixir-rfc-mixed_number_detection`
- **Finding ID:** `CSCAN-elixir-rfc-mixed_number_detection`
- **Severity:** Low
- **Clause:** MIXED_NUMBER_DETECTION — Only Decimal_Number (Nd) digits should be allowed and mixed decimal number systems detected. (cites: Unicode UTS #39 §5.3) (quote: "Only numbers with General_Category") [SHOULD]
- **RFC:** 
- **Location:** /Users/lukas/code/claude-scanner/elixir/lib/elixir/unicode/tokenizer.ex:483-522 (validate/2, mixed-script branch — no mixed-number branch); premise stated at pages/references/unicode-syntax.md:147
- **Evidence:** `tokenizer.ex:77` adds General_Category `Nd` to `continue`, and IdentifierType.txt shows recommended-script decimal digits (e.g. `0966..096F ; Recommended` — Devanagari digits, Nd) survive the `-- restricted` filter (`tokenizer.ex:112-129`), so they land in `id_continue`/`unicode_continue` and ARE tokenizable as identifier continue chars. `validate/2` performs only NFC + mixed-script (scriptset-intersection) checks; grep across `unicode/*.ex` and `elixir_tokenizer.erl` for `number system`/`decimal`/`Nd`/mixed-number found no per-digit "single decimal number system" test. ASCII digits resolve to `@top` (`codepoint_to_scriptset`, line 575-576), so an identifier like Devanagari-letter + ASCII `0` + Devanagari `०` keeps a non-empty (Devanagari) scriptset and passes, mixing two decimal number systems undetected.
- **Suggested fix:** Add a mixed-number check in `validate/2`: for all Nd codepoints in the accumulator, compute the digit's zero-base (codepoint − Digit_Value) and reject the identifier if more than one distinct base is present; otherwise genuinely bar non-ASCII Nd from identifiers so the "does not support Unicode numbers" claim holds.

The clause (UTS #39 §5.3, SHOULD) has two conjuncts: only Nd digits allowed (satisfied — only `Nd` is added at tokenizer.ex:77, not `No`), and mixed decimal number systems detected (not satisfied). The doc at unicode-syntax.md:147 declares "C5 – Mixed number detection … inapplicable as Elixir does not support Unicode numbers," but that premise is false: I confirmed via UnicodeData.txt (Devanagari digits are Nd) and IdentifierType.txt (they are `Recommended`, hence not stripped by the restricted filter) that recommended-script Unicode decimal digits are accepted as identifier continue characters. Because the mixed-script scriptset check treats ASCII digits as `@top` and same-script digits as script-neutral within their script, an identifier can legally combine ASCII and another script's Nd digits with no rejection — precisely the case §5.3 asks implementations to detect. The purported non-goal rests on an incorrect factual premise, so this is an omission owed rather than an architectural boundary; severity is Low given the SHOULD level and the deliberately-crafted, narrow spoofing scenario.

#### `CSCAN-elixir-rfc-implicit_level_resolution`
- **Finding ID:** `CSCAN-elixir-rfc-implicit_level_resolution`
- **Severity:** Low
- **Clause:** IMPLICIT_LEVEL_RESOLUTION — assign implicit levels so numbers embedded in RTL runs are not visually reversed together with the surrounding strong RTL characters. (cites: Unicode UAX #9 §3.3.6 I1/I2) (quote: "A sequence of NIs takes the direction of the surrounding strong text") [SHALL]
- **RFC:** 
- **Location:** /Users/lukas/code/claude-scanner/elixir/lib/elixir/unicode/security.ex:171-172 (`:weak_number` clause of `unbidify/1`)
- **Evidence:** The simplified reordering in `unbidify/1` (the folder's UAX #9-based bidi skeleton, used by `bidi_skeleton/1`→`confusable_skeleton/1`) handles `:weak_number` (digits 0-9, per `tokenizer.ex:350`) by `{[], part_dir, [head] ++ neutrals ++ part, acc}` — prepending each digit individually to the current RTL part just like a strong RTL char. Since an RTL part is built by prepending and then not internally re-reversed, this reverses the internal order of multi-digit numbers. I ran the exact reduce logic standalone: logical `[Aleph(rtl), "1", "2"]` → `["2","1",Aleph]`, and `[Aleph,"1","2",Bet]` → `[Bet,"2","1",Aleph]`. The UAX #9 I1/I2 result (paragraph level 1; EN bumped to even level 2; L2 double-reversal) is `["1","2",Aleph]` — digits must stay LTR. Code yields `["2","1",Aleph]`.
- **Suggested fix:** In the `:weak_number` case, accumulate consecutive digits preserving their logical order and splice the group into the part without per-digit prepending (i.e. bump the number to an even level so it isn't reversed with the surrounding RTL run), so `[Aleph,"1","2"]` reorders to `["1","2",Aleph]`.

This folder does implement the UAX #9 reordering component the clause governs — `unbidify/1` is explicitly the "drastically simplified" bidi algorithm (comments at security.ex:159-166 cite UTS39-28 §4 and W2) used to build the bidi confusable skeleton, so the clause applies and is not owned elsewhere. Tracing the call graph: `confusable_skeleton/1` (line 106) → `bidi_skeleton/1` (line 126) → `unbidify/1` (line 166) for any identifier containing R/AL characters. I verified empirically by copying the verbatim `Enum.reduce` logic into a standalone script with a mock `dir/1` returning the same atoms; for numbers embedded in an RTL run the digits come out reversed together with the strong RTL characters, which is exactly what I1/I2 forbids ("numbers embedded in RTL runs are not visually reversed together with the surrounding strong RTL characters"). Impact is limited to inaccurate confusability *warnings* (a whole-file lint, not a hard rejection) for the niche case of multi-digit numbers adjacent to RTL characters in identifiers, hence Low severity — but it is a genuine SHALL-level conformance gap, not a mere strictness nitpick.

## Satisfied & not-applicable clauses

- **IDENTIFIER_START_CONTINUE_SYNTAX** — ✅ satisfied — `id_start` is built from UnicodeData categories Lu/Lt (id_upper) + Ll/Lm/Lo/Nl + PropList `Other_ID_Start`; `id_continue` from Mn/Mc/Nd/Pc + `Other_ID_Continue` (lines 71-78, 96-97); `Pattern_Syntax`/`Pattern_White_Space` subtracted (`-- patterns`, 127-129). `tokenize/1` admits a start char only via `unicode_upper`/`unicode_start`/`normalize_start`, else `{:error, :empty}` (389-393); `continue/6` admits a continue char only via ascii or `unicode_start`/`unicode_upper`/`unicode_continue`/`normalize_start`, else `{:error, {:unexpected_token,...}}` (440-445) — every other codepoint is rejected.
- **PATTERN_SYNTAX_WHITESPACE_DISJOINT** — ✅ satisfied — `PropList.txt` is parsed collecting `Pattern_White_Space` and `Pattern_Syntax` ranges into `patterns` (tokenizer.ex:98-99, both mapped to elem index 2); then `id_upper`/`id_start`/`id_continue` are each computed as `(… -- patterns) -- restricted` (lines 127-129), removing every Pattern_Syntax and Pattern_White_Space code point from all three identifier sets that feed the generated `String.Tokenizer`.
- **IDENTIFIER_STABILITY** — ✅ satisfied — `id_start`/`id_continue`/`id_upper` (tokenizer.ex:127-129) are derived from the standard UCD categories `L,Nl,Mn,Mc,Nd,Pc` plus `Other_ID_Start/Continue` (lines 70-108) minus `Pattern_Syntax`/`Pattern_White_Space` — exactly the UAX #31 default-identifier derivation whose constituent properties Unicode's own stability policy guarantees to be monotonic across versions; unicode-syntax.md:51,75 explicitly identifies conformance to UAX #31 v17.0 and states "R1b is guaranteed for backwards compatibility purposes", and the pinned data version is queryable via `String.Unicode.version()` (unicode-syntax.md:16).
- **NFC_NORMALIZATION_EQUIVALENCE** — ✅ satisfied — In `String.Tokenizer.validate/2`, non-ASCII identifier accumulators are rewritten to NFC via `acc = :unicode.characters_to_nfc_list(original_acc)` (tokenizer.ex:474) and the NFC `acc` is what is returned as the token (line 488) and later interned into the atom by `keyword_or_unsafe_to_atom` in elixir_tokenizer.erl:1408-1409; ASCII identifiers (line 469) are NFC by definition. The Normalization Form is explicitly specified as NFC and the excluded characters (quoted atoms and strings) are precisely stated in unicode-syntax.md:24, 59-65, 103-111.
- **CONFORMANCE_VERSION_IDENTIFIED** — ✅ satisfied — `def version, do: {17, 0, 0}` exposes the UCD data version at runtime; the conformance page states verbatim "Elixir conforms to ... Unicode Standard Annex #31 ... version 17.0" (line 51) and "Unicode Technical Standard #39 ... version 17.0" (line 115); UCD data files (`Scripts.txt:1`, `PropList.txt:1`, `IdentifierType.txt:8`, `SpecialCasing.txt:1`, `PropertyValueAliases.txt:1`) all carry the `17.0.0` version header they were built from.
- **RESTRICTED_CHARS_EXCLUDED** — ✅ satisfied — The `restricted` set is built from `IdentifierType.txt` keeping only code points whose types include `Inclusion` or `Recommended` (lines 116-125), i.e. `Identifier_Status=Allowed` per UTS #39; everything else is Restricted. It is then subtracted from every identifier set: `id_upper = (letter_uptitlecase -- patterns) -- restricted`, `id_start = (start -- patterns) -- restricted`, `id_continue = (continue -- patterns) -- restricted` (lines 127-129). The one documented exception (U+00B5 µ → U+03BC μ start-normalization) is declared and its exemption explained in the header comment (lines 8-20: "similarly, they are exempted from the Restricted list").
- **CANONICAL_EQUIVALENCE_NORMALIZATION** — ✅ satisfied — In `validate/2` every non-ASCII candidate identifier's code points are run through `:unicode.characters_to_nfc_list(original_acc)` (line 474 — NFC is the canonical composition form), and the token is emitted in that NFC form (`{kind, acc, ...}` line 488).
