# Prompts used for this scan
<!-- guidance-sha256: 87902c25b6409c1f0b3a2351d0f1c0aeabb7de5abb9a021ae4a7a41c81ea173a -->


This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert Erlang programmer performing a focused bug-hunting review of a single Erlang source file. Review only this file:

${FILE}

Your sole topic is **bugfixes**: defects that make the code do the wrong thing, crash, hang, corrupt data, leak resources, or violate its own documented contract, when reached through a documented public API.

## Scope — what counts

Focus exclusively on bugs reachable through the module's **documented public API**. Ignore, and do not report, any finding that is only reachable through misuse of internal interfaces. Specifically exclude:

- Bugs reachable only by calling private / non-exported / non-public-API entry points, by sending crafted messages to undocumented internal processes, or by depending on implementation details that are not part of the documented public API.
- Bugs that require the caller to pass arguments which violate the function's documented type spec / contract / header declaration. Erlang does not enforce specs at runtime, so a caller who breaks the contract is uninteresting.

Do **NOT** exclude bugs where untrusted data reaches vulnerable code through a documented public API — even if exploitation requires an attacker. This includes parser/decoder bugs on network input, file-format handling, and any code path callable from a documented entry point. A `badmatch`/`function_clause`/`case_clause` on an input the spec did not explicitly forbid, reached from a public entry point, is in scope.

You must not modify any files. Output only the markdown report described at the end.

## Phase 1 — inventory (do not skip)

The classes below are a *coverage floor*, not a ceiling. They list failure shapes that have historically caught bugs in Erlang stdlib / OTP code; use them to be thorough, not as an enumeration of possibility. Bug findings outside the list are first-class — the `Unclassified` class at the end is where they go, and force-fitting a finding into a class that doesn't actually apply is worse than declaring it `Unclassified`. A failure mode is dangerous regardless of whether the file currently looks dangerous — enumerate first, judge second.

- **Operator / precedence typo** — `andalso` where `orelse` was meant, `,` where `;` was meant in a guard, `==` instead of `=:=`, missing parentheses that change associativity. The classic shape: a guard or boolean expression that "looks right" but is satisfied by an empty / nonsensical set of inputs, or by *every* input.
- **Missing clause / catch-all** — a function head that handles N input shapes but not the (N+1)th the protocol or caller actually produces; a `case` without a fall-through clause that crashes on a benign input; a `try ... catch error:_` that omits `throw:` or `exit:`.
- **Wrong atom / wrong symbol** — checking for an atom name that doesn't exist (e.g. `background_color` when the real key is `background`), a copy-paste BIF name (`adler_combine` instead of `adler32_combine`), or a record field name that has drifted.
- **State / accumulator threading error** — using a stale variable (`St0`) after a later rebind (`St1`), passing an unchanged accumulator into a recursive call, returning the wrong half of a tuple, or dropping a flag (e.g. `hibernate`) across a refactor.
- **Off-by-one / wrong arithmetic** — `length(LA)` lines when the cursor should land on line 1; mixing milliseconds and microseconds in a timeout calculation; size = N when N+1 is required; `rem N` where the intent was `div N`.
- **Contract violation** — a function that returns a shape its docstring or `-spec` does not declare (`{Result, Y, Z}` instead of the documented `{Result, Y}`, a bare atom instead of `{error, Reason}`, a `{noreply, _}` from a `gen_server:call`-only handler with `infinity` timeout — which then hangs).
- **Crash on stray / unexpected input** — `badmatch` / `function_clause` / `case_clause` reachable from a documented API on an input the spec did not explicitly forbid (stray `'DOWN'` message, custom formatter return shape, malformed `Mod:init/1` return, over-long startup argument).
- **Resource leak on error path** — file handle / ETS table / process / monitor / counter created in a cleanup-on-success branch but leaks when a sibling clause raises, when `cleanup` is called with the wrong state, or when `catch throw` doesn't catch `error`/`exit`.
- **Silent corruption** — function returns a value that *looks* right but is wrong (writes callback specs under a `function` key, truncates events past 64KiB, returns `Secs rem 1_000_000` instead of `Secs`, discards an accumulator on the empty-map clause). The user sees no error — only later breakage downstream.
- **Infinite loop / hang** — an unguarded `receive` whose sender can die without sending the awaited message; recursion that doesn't decrease in any meaningful sense (symlink cycles, retry without a counter); a catch-all `handle_call` returning `{noreply, …}` against an `infinity` caller.
- **Quadratic-where-linear** — `Acc ++ X` in a tail-recursive loop (the classic stdlib offender); `<<X, BHead/binary>>` prepended in a loop; `length/1` in a guard or per-iteration check; repeated `lists:member/2` as a "visited" set; rebuilding a map iterator on every step.
- **Repeated work** — recompiling a `binary:compile_pattern/1` on every match; opening + scanning the same BEAM twice per request; calling `external_size/1` on every cache update; re-stat'ing every entry in a recursive directory walk; rebuilding a 48-atom list every call to a `is_*/1` predicate.
- **Dead / unreachable code** — branches the dispatcher can never reach; "asserts — remove me" leftovers that double the cost of every call; a documented `expand/2` invariant maintained "by accident" in a later pass; a `format_section`-per-doc helper that's effectively dead code because the caller short-circuits.
- **Documented behaviour mismatch** — function doesn't do what its docstring or `-spec` promises (`bytes_s(0, S)` advances PRNG when docs say it's stateless; `slave:start/3` documented to return `{error, Reason}` but badmatches on lookup failure). Compare against the comment block / `@doc` / type spec for every public entry point you review.

  Two rules make this class actually bite, because it is the easiest one in the list to dismiss for the wrong reason.

  (a) **Enumerate the documented CLAIMS; running the documented examples does not discharge this class.** The examples were chosen by the same author who wrote the prose, so they systematically exclude the cases that author did not think of — they cannot falsify the author's own misconception. Take each prose sentence that asserts something ("anything else is ignored", "returns the first match", "the list is unchanged", "safe to call concurrently") and construct an input that would expose it if it were false. `proplists:to_map/1` documents "Anything else will be silently ignored" while a tuple of arity /= 2 removes that key — `to_map([{c,3,4},{c,2}])` is `#{}`, not `#{c => 2}`. A review that hand-traced the moduledoc's own examples reproduced them all exactly and marked the class `verified`.

  (b) **The code's internal rationale is not the specification.** When behaviour has a coherent reason that differs from the documented reason, that coherence is what makes the wrong answer convincing — everything genuinely does check out, just against the wrong reference. In the same module, `to_map/1` faithfully mirrors `get_value/2`'s early-return rule on every ordering, which is exactly why three separate dismissals concluded it was fine: they verified it against its sibling function instead of against its documentation. Verify against the documented contract. If the code is self-consistent but contradicts the docs, that is a finding, not a reason to close one — and say which side you think should change.

- **Race condition / shared mutable state** — `erlang:system_flag/2` flipped without coordination across concurrent callers; `gen_*` table state read-then-written without `gen_server:call`; a worker spawned without `link` or `monitor` so its death isn't observed.
- **Wrong scope / order of operations** — `spec_decl` overwriting `Anno` before the redefine check that needs the original; performing a side-effect before validating its inputs; `cleanup` runs with the initial state (`out=undefined`) instead of the captured one.
- **Encoding / unicode mishandling** — treating bytes as codepoints; `lists:flatten/1` on a chardata input (crashes on improper lists); `is_color`-style atom check that ignores the encoding the caller requested; defaulting to Latin-1 in a UTF-8 sink.
- **Unclassified** — anything bug-relevant that doesn't fit the classes above. Novel patterns, composite issues, file-specific one-off sins, protocol-state confusions that span several shapes — all live here. If you'd be uncomfortable defending the code to a sceptical reader asking "are you sure this is what it's supposed to do?", flag it under Unclassified and describe the shape of the bug. This class exists specifically so you don't have to force-fit a finding into a class that doesn't apply.

## Phase 2 — per-failure, in order

For each finding in the inventory: (1) name the function/line and the specific shape of the bug. (2) Describe how the bug is triggered — a documented public API call, a callback delivered to a `gen_*`, a sys-debug-enabled call path, a malformed-but-legal input. If you cannot construct a trigger, that is itself a finding (under "Dead / unreachable code"). (3) State the **user-visible bad outcome**: what incorrect behaviour does the caller actually observe? (4) Rate Critical / High / Medium / Low.

### Phase 2 — additional obligations

**Spec-totality**: a `-spec` is trusted, not verified — a function that accepts less than it declares passes Dialyzer in silence, and the miss lives in the constructors nobody enumerated. A generated checklist of this file's exports with non-builtin spec types is prepended to this review; answer it entry by entry, one line per covered entry. The lens goes to every export, not to the ones that look interesting.

For every reachability claim:

- **Reachability** — construct an input that triggers the bug starting from a documented public API entry point. Walk the dispatcher / parser / state-machine clause that delivers it. If the file is a library module, name the documented function that callers use to invoke the buggy path.

For every claim made in the report about other files (callers, callees, included headers, behaviour modules):

- **Assumptions enumeration** — list each assumption explicitly. State what would change if the assumption is wrong, and whether the change would upgrade a ruled-out failure mode to a finding. A claim like "callers pass well-formed input here" without an enumerated assumption is a finding by default — the audit must declare its dependence on out-of-file behaviour.

### Common slip-up patterns to actively look for

These shapes have historically been mis-coded and are cheap to grep for. Look once per file regardless of where the file sits in the taxonomy:

- Guards using `,` and `;` — `,` binds tighter than `;`. Read each guard with explicit parentheses and confirm the partition matches the intent.
- `try ... catch _:_` and `catch _ -> ...` — confirm which exception classes are actually caught. `catch _` catches `throw` only.
- `length(L) > N` used as a precondition that should accept binaries too — guards silently fail for non-lists.
- `Acc ++ X` inside a recursive accumulator — should be `[X | Acc]` with a single `lists:reverse` at the end.
- `==` between Erlang terms where `=:=` is intended (or vice versa when matching against integers vs floats).
- `lists:keyfind` / `lists:member` used as a visited set in a loop — should be a `map` / `set` / `gb_set`.
- Recompiled patterns inside loops: `binary:compile_pattern`, `re:compile`, `ets:fun2ms` inside per-call code.
- Catch-all `handle_call` clauses returning `{noreply, _}` against callers using `gen_server:call(_, _, infinity)`.

## Output format

Produce a concise markdown report and nothing else — no preamble, no trailing commentary, and do not modify any files. The report has these sections in this order:

1. **Summary** — exactly one sentence.
2. **Bugfixes** — one bulleted findings section (this is the only topic). Format each finding as specified below. If nothing meaningful is found, write `No findings`.
3. **Risks / caveats** — closing section.

### Output for bug findings

Begin each finding with a level-4 markdown heading containing only its Finding ID wrapped in backticks, on its own line, e.g.:

    #### `CSCAN-<file-basename>-<short-mnemonic>`

GitHub turns that heading into a stable `#cscan-…` anchor, so the finding can be linked to directly from the summary and the cross-scan indexes. Immediately below the heading, write these fields on separate lines, in this order:

- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the bug semantics (e.g. `CSCAN-erl_tar-pax-time-rem`, `CSCAN-io_lib-write-bin1-empty-map-drops-acc`, `CSCAN-edlin_expand-guard-comma-typo`). Derive it from *what the bug is*, not from finding-order — re-scans of the same file should produce the same ID for the same bug, so downstream tracking (issue trackers, fix-commit messages, PR comments) can reference it stably. Keep mnemonics under 40 characters and avoid version numbers, line numbers, or anything that drifts.
- **Severity** — Critical / High / Medium / Low. Use Critical only for silent broad-impact corruption or hangs in a documented public API; High for subtle bugs in common paths or large scalability problems; Medium for notable correctness or perf issues in a contained area; Low for small or cosmetic findings (style, dead code with no current impact, tail-recursion misses).
- **Confidence** — high / medium / low (definitions below).
- **Location** — file:line and the function/clause name.
- **Class** — the Phase 1 failure-mode class this finding belongs to, or `Unclassified (<short free-text label>)` if the finding genuinely doesn't fit. Force-fitting a finding into a class that doesn't apply is worse than declaring `Unclassified`.
- **User-visible outcome** — a short narrative (1–3 sentences) describing what an end-caller of this code actually observes when the bug fires. Be concrete: "the extracted file's mtime is 1970", "a `bwrite([1, #{}, 2], [])` returns `<<\"#{},2]\">>`", "`gen_server:call` hangs forever on any unexpected message". **End the outcome paragraph with one sentence answering: "What incorrect behaviour does this produce that a caller would notice that wouldn't be there without this bug?"** If the answer is "nothing a caller would notice" — e.g. a `function_clause` that only fires on inputs `-spec` already declares illegal, or a leak that the BEAM garbage-collects on the next minor GC, or a perf win that's bounded by a cheap upstream check — the finding is most likely defensive-tightening or style, not a bug. In that case re-rate severity and confidence accordingly (Low/low at most) and consider whether it belongs as a finding at all rather than under `### Ruled out`. The user-visible-outcome sentence is mandatory and is what distinguishes a real bug from "the code could be tidier."
- **Reproduction** — a short concrete sketch: an input that triggers the bug, or a call sequence from a documented entry point, or a stacktrace shape. Name any guard or upstream check a naïve attempt would hit first.
- **Suggested fix** — concrete change (function/line and the new behaviour). Keep it minimal — the smallest diff that fixes the bug, not a refactor.
- **Risk of fix** — any observable behaviour change a downstream consumer might depend on. Tests that may break, error shapes that may change, perf characteristics that may shift. State "none" if the fix is obviously safe.
- **Evidence** — name the source(s) backing this finding. Write one or more lines, picking the strongest available. Each line is one of:
  - `read <path>:<lines>` — you used the `Read` tool on the cited range. Most findings should carry at least one such line.
  - `ran <command>` (followed by a one-line excerpt of output) — you used the `Bash` tool. **Do not write `ran` if you did not actually run the command** — claiming empirical verification you did not perform invalidates the finding.
  - `relies on <other_file_report>: <one-line claim>` — citing another per-file report (cross-file dependency; verified by the cross-file pass).
  - `inferred from <name/signature>` — reasoning from a name or type spec without reading the implementation. Auto-downgrades the finding to Confidence: low.

  Forbidden phrases (without a matching `ran` evidence line): "I empirically tested", "I empirically verified", "I confirmed runtime behaviour", "I ran X and observed Y". Read/Grep/Glob do not execute code.

Confidence is one of `high`, `medium`, `low`:

- **high** — verified the bug class is real, reachable from a documented public API, and the user-visible outcome is real. The reviewer read the relevant code paths and can name them.
- **medium** — bug class is real and likely reachable; triggering requires reasonable but unverified caller behaviour or a plausible-but-not-confirmed code path.
- **low** — defensive-tightening concern, style issue, or hypothetical case where the bug needs a future change or undocumented usage to become observable.

The impact/threat note for the bugfixes topic is the **User-visible outcome** field plus the **Severity** rating: state concretely what a caller observes and how bad it is.

### Ruled out

After the findings, append a `### Ruled out` section listing every Phase 1 failure-mode class that did not become a finding. Listing ruled-out classes is required when Phase 1 found any — it is how the audit demonstrates it actually considered them. For each ruled-out class, write these fields on separate lines:

- **Reason** — one sentence on why it's not a finding.
- **Axes examined** — the input-space axes you actually tried against this failure-mode class, then the ones you did not, as two lists on one line:
  `Axes examined: empty list, single element | Not examined: improper list, unicode binary, negative integer`
  An axis is a shape of input the class could trigger on that a different shape would not: empty / single / very large collection, improper list, unicode vs latin1 binary, negative and zero integers, float-int boundary, atom vs binary vs list for the same value, missing optional field, duplicate key. Name the axes belonging to the datatype in front of you — "I read the clause" is not an axis. "Tried" means you ran the input through the code and observed the result (run it if the toolchain is there). Write `Not examined: none` only when you enumerated the datatype's axes and tried every one.
- **Basis** — either `verified` or `asserted`. `verified` requires BOTH that you read the relevant code and traced the trigger explicitly AND that `Not examined` is `none`. Reading a clause tells you what it matches, not which inputs it fails to match; a dismissal that leaves axes untried is not substantiated. Everything else is `asserted` — you inferred from the function name, docstring, or absence of obvious red flags without reading the code, or you read the code but left axes untried. Mark every `asserted` ruling-out as low-confidence; a future hedge-triggered re-run will revisit them.
- **Depends on** (**REQUIRED when Basis is `asserted`**) — name the specific file path, module, or invariant the dismissal relies on, with a one-line description of the contract being assumed. The cross-file pass enumerates every `Depends on:` line and either confirms the dependency against the cited module's own report or treats the dismissal as an open finding. Without this line, an asserted dismissal is unverifiable.

### Did I verify this?

After the "Ruled out" section, write a `### Did I verify this?` section that walks every ruled-out entry and re-checks the Basis honestly. For each `asserted` ruling-out, either upgrade it to `verified` — which means reading the code now AND trying every axis still on its `Not examined` list, until that list reads `none` (then remove the `Depends on:` line) — or keep it `asserted` with the explicit `Depends on:` line naming where the verification needs to happen. Re-reading the code never on its own upgrades a dismissal whose `Not examined` list is non-empty: the untried axes are precisely what a re-read does not cover. The point of this section is to catch the failure mode of dismissing a class with a plausible-sounding paragraph that the reviewer did not actually substantiate.

### On ruling something out

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof, not the lightest. A ruled-out entry whose Basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. A false positive is caught downstream by the validator; a false negative is invisible, which is why the asymmetry runs this way.

Every claim of absence is a claim about a search space, and it stands only when the space and the search are named. Three shapes smuggle one in without naming it:

- A negative existence claim from a partial search. "This module has no X" quantifies over everything in scope, not over the files you opened. Name where you looked, or the Basis is `asserted`.
- A parity claim without the upstream mechanism. "Matching upstream behaviour" asserts the absence of a difference. Name the mechanism and its default — "OpenSSH caps this at `MaxSessions`, default 10" is a comparison; "OpenSSH behaves the same" is not.
- A mitigation the threat model does not grant. "Requires authentication" asserts the attacker's absence past a door the threat model may hold open. For a server that accepts credentials from the network, post-auth IS the attack surface.

Write `No findings` under the Bugfixes section if nothing meaningful is found. Do not modify any files. Output only the markdown report.
````
