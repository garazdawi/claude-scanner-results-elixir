# Compliance ledger — elixir
<!-- 1 standard(s), 48 clause(s) (exhaustive per-RFC enumeration) -->

## Consolidated clauses
1. IDENTIFIER_START_CONTINUE_SYNTAX — Tokenizer admits identifiers only as Start Continue* built from XID_Start/XID_Continue-derived categories (L, Nl, Mn, Mc, Nd, Pc, Other_ID_Start/Continue), rejecting any other codepoint. (cites: Unicode UAX #31 §R1/R1-1) (quote: "setting Start and Continue to the properties XID_Start and XID_Continue, respectively, and leaving Medial empty") [SHALL]
2. PATTERN_SYNTAX_WHITESPACE_DISJOINT — Characters allowed in identifiers, whitespace, and syntax characters must be mutually disjoint (Pattern_Syntax and Pattern_White_Space subtracted from the identifier sets). (cites: Unicode UAX #31 §R3b-1) (quote: "The following sets shall be disjoint: (1) characters allowed in identifiers (2) characters treated as whitespace (3) characters with syntactic use") [SHALL]
3. IDENTIFIER_STABILITY — Once a string qualifies as an identifier it must remain an identifier across future Unicode versions. (cites: Unicode UAX #31 §R1b) (quote: "once a string qualifies as an identifier, it does so in all future versions of the Unicode Standard") [SHALL]
4. NFC_NORMALIZATION_EQUIVALENCE — Implementation must specify a Normalization Form, precisely specify excluded characters, and treat identifiers with the same normalized form as equivalent (Elixir normalizes atoms/variables to NFC; quoted atoms/strings excluded). (cites: Unicode UAX #31 §R4) (quote: "any two identifiers that have the same Normalization Form shall be treated as equivalent by the implementation") [SHALL]
5. CONFORMANCE_VERSION_IDENTIFIED — A conforming implementation must identify the version of the specification (and, consistently, the Unicode data version its identifier/script tables are built from). (cites: Unicode UAX #31 §C1) (quote: "An implementation claiming conformance to this specification shall identify the version of this specification") [SHALL]
6. RESTRICTED_CHARS_EXCLUDED — Identifiers must not admit characters with Identifier_Status=Restricted unless the added set is documented. (cites: Unicode UTS #39 §3.1) (quote: "unless it documents the additional characters that it does allow") [SHALL]
7. CANONICAL_EQUIVALENCE_NORMALIZATION — Canonical equivalence must be applied when testing candidate identifiers for the Allowed set. (cites: Unicode UTS #39 §3.1) (quote: "Canonical equivalence is applied when testing candidate identifiers for inclusion of") [SHALL]
8. JOINING_CONTROLS_LIMITED — ZWNJ/ZWJ (Join_Control) may only be admitted in the specified limited joining/virama contexts. (cites: Unicode UTS #39 §3.1.1) (quote: "should allow the following Join_Control characters in the limited contexts") [SHOULD]
9. CONFUSABLE_SKELETON — Confusable detection must compute the skeleton (NFD, concatenate prototypes, reapply NFD) so that X and Y are confusable iff their skeletons are equal, with transitivity. (cites: Unicode UTS #39 §4) (quote: "if X ≒ Y (𝑑) and Y ≒ Z (𝑑), then X ≒ Z (𝑑)") [SHALL]
10. BIDI_SKELETON — Directional confusability must be detected via bidiSkeleton (apply the bidi algorithm before skeletonizing). (cites: Unicode UTS #39 §4) (quote: "bidiSkeleton(𝑑, X) = bidiSkeleton(𝑑, Y)") [SHALL]
11. AUGMENTED_SCRIPT_SET — Script sets must be augmented with {Hanb, Jpan, Kore} per constituent scripts, and Common/Inherited treated as ALL scripts. (cites: Unicode UTS #39 §5.1) (quote: "the intersection of the augmented script sets over all characters in the string") [SHALL]
12. MIXED_SCRIPT_DETECTION — A string is single-script iff the resolved (intersected) script set is nonempty, else mixed-script; mixed-script identifiers must be rejected/flagged. (cites: Unicode UTS #39 §5.1) (quote: "if its resolved script set is empty") [SHALL]
13. RESTRICTION_LEVEL_ENFORCED — Identifiers must satisfy a restriction level (ASCII-Only / Single-Script / Highly Restrictive covering Latin+Han+Kana/Bopomofo/Hangul). (cites: Unicode UTS #39 §5.2) (quote: "Latin + Han + Hiragana + Katakana") [SHALL]
14. MIXED_NUMBER_DETECTION — Only Decimal_Number (Nd) digits should be allowed and mixed decimal number systems detected. (cites: Unicode UTS #39 §5.3) (quote: "Only numbers with General_Category") [SHOULD]
15. SCX_INCLUDES_SCRIPT_VALUE — an explicit Script (sc) value of a code point must also appear in that code point's Script_Extensions (scx) set; the union built from Scripts.txt + ScriptExtensions.txt must reflect this. (cites: Unicode UAX #24 §3.1) (quote: "that value must be an element of the scx set for that code point as well") [MUST]
16. COMBINING_MARK_NO_SCRIPT_BREAK — when determining script boundaries, do not break between a combining/nonspacing mark and its base character (Inherited marks must not split a script run). (cites: Unicode UAX #24 §5.2) (quote: "should never break") [SHOULD NOT]
17. COMBINING_SEQUENCE_INHERITS_FIRST_SCRIPT — treat every character of a combining character sequence as having the Script value of the first (base) character rather than as its own script. (cites: Unicode UAX #24 §5.2) (quote: "recommended implementation strategy is to treat all the characters of a combining character sequence") [RECOMMENDED]
18. SCRIPT_MATCH_WITH_COMMON_INHERITED — when testing script membership, specific Script values must be combined with Common and Inherited (so direction-neutral/Common/Inherited chars match any script). (cites: Unicode UAX #24 §5.4) (quote: "should use specific Script property values only in conjunction with both") [SHOULD]
19. FIELD_SEMICOLON_SEPARATION — UCD data lines are parsed into fields split on semicolons, numbered from zero. (cites: Unicode UAX #44 §4.2.1) (quote: "Each line of data consists of fields separated by semicolons.") [MUST]
20. FIELD_TRIM_SPACES — leading/trailing whitespace within a field is stripped before interpreting the value. (cites: Unicode UAX #44 §4.2.1) (quote: "Leading and trailing spaces within a field are not significant.") [MUST]
21. CODEPOINT_HEX_PARSE — the code-point field(s) are read as hexadecimal numbers of four to six digits. (cites: Unicode UAX #44 §4.2.2) (quote: "Code points are expressed as hexadecimal numbers with four to six digits.") [MUST]
22. CODEPOINT_SEQUENCE_SPACE_SPLIT — a field holding multiple code points is split on spaces into the sequence. (cites: Unicode UAX #44 §4.2.2) (quote: "When a data field contains a sequence of code points, spaces separate the code points.") [MUST]
23. RANGE_DOTDOT_EXPANSION — a code-point range written "X..Y" is expanded so every point in it carries the row's property value. (cites: Unicode UAX #44 §4.2.3) (quote: "A range of code points is specified by the form 'X..Y'.") [MUST]
24. UNICODEDATA_FIRST_LAST_RANGE — ranges in UnicodeData.txt are given as paired First/Last angle-bracket entries, not "X..Y", and must be reconstructed. (cites: Unicode UAX #44 §4.2.3) (quote: "ranges in the file UnicodeData.txt are specified by entries for the start and end characters of the range") [MUST]
25. DECOMP_TAG_COMPAT_VS_CANONICAL — a Decomposition_Mapping beginning with an angle-bracket tag is a compatibility mapping and is treated differently from a bare (canonical) mapping. (cites: Unicode UAX #44 §5.7.3) (quote: "compatibility mappings are given with a formatting tag in angle brackets") [MUST]
26. DECOMP_DEFAULT_SELF — a code point absent from the decomposition data defaults to decomposing to itself. (cites: Unicode UAX #44 §4.2.9) (quote: "including the definition of foldings and mappings, the default value is the code point of the character itself") [MUST]
27. COMBINING_CLASS_NUMERIC — the Canonical_Combining_Class field is parsed as its numeric value (0 meaning not-reordered). (cites: Unicode UAX #44 §4.2.9) (quote: "For the Canonical_Combining_Class property, the default value is 0.") [MUST]
28. CASE_MAPPING_DEFAULT_SELF — Simple_Uppercase/Lowercase mappings default to the character itself when the field is empty. (cites: Unicode UAX #44 §4.2.9) (quote: "For most string-valued properties ... the default value is the code point of the character itself") [MUST]
29. SPECIALCASING_FULL_OVER_SIMPLE — SpecialCasing.txt full mappings are combined with UnicodeData.txt simple mappings, with conditional entries separated from unconditional ones. (cites: Unicode UAX #44 §SpecialCasing.txt) (quote: "in combination with the simple case mappings from UnicodeData.txt) the full case mappings") [MUST]
30. MISSING_DEFAULT_VALUES — code points omitted from a data file take the property's default value as declared by @missing conventions. (cites: Unicode UAX #44 §4.2.10) (quote: "the keyword \"@missing\" are used to define default property values for ranges of code points not explicitly listed") [MUST]
31. BINARY_PROP_DEFAULT_N — a binary property (e.g. Other_Lowercase/Other_Uppercase from PropList) is False for any code point not listed. (cites: Unicode UAX #44 §4.2.9) (quote: "For binary properties except for Extended_Pictographic, the default value is always 'N' (= False).") [MUST]
32. PROPERTY_VALUE_ALIASES — property values (e.g. General_Category codes) are interpreted via the aliases defined in PropertyValueAliases.txt. (cites: Unicode UAX #44 §5.7.5) (quote: "the second field specifies the name of the property and the third field specifies the property value") [MUST]
33. DERIVED_USE_EXPLICIT_LISTING — derived properties should be taken from their explicit data listing rather than re-derived from simple properties and rules. (cites: Unicode UAX #44 §2.1.2) (quote: "the explicit listing in the data file should _always_ be taken as the normative definition") [SHOULD]
34. VERSION_STABILITY_PINNED — the implementation is bound to one published, immutable UCD version. (cites: Unicode UAX #44 §2.3) (quote: "each version of the UCD, once published, is absolutely stable and will _never_ change") [MUST]
35. NF_PRODUCTION_CONFORMS — Any routine emitting text as a Normalization Form (String.normalize/2 for :nfd/:nfc/:nfkd/:nfkc; tokenizer NFC pass) must produce output actually conforming to the §3.11 form definitions. (cites: Unicode UAX #15 §Conformance C1) (quote: "produces Unicode text that purports to be in a Normalization Form shall do so in accordance with the specifications in Section 3.11") [SHALL]
36. NF_TEST_CONFORMS — Testing whether text is in a Normalization Form / is canonically equivalent (String.equivalent?/2 comparing NFD forms) must follow the §3.11 specifications. (cites: Unicode UAX #15 §Conformance C2) (quote: "tests Unicode text to determine whether it is in a Normalization Form shall do so in accordance with the specifications in Section 3.11") [SHALL]
37. NORMALIZE_MATCHES_CONFORMANCE_DATA — The transform-to-NF path must reproduce the reference results of NormalizationTest.txt (correct canonical/compatibility decomposition, canonical ordering, and canonical composition for every form). (cites: Unicode UAX #15 §Conformance C3) (quote: "must be able to produce the results of the conformance test specified in the NormalizationTest.txt data file") [MUST]
38. REORDER_TO_DISPLAY_ORDER — resolve embedding levels and reorder the input so the checked sequence matches the perceived/display order, per the algorithm's steps. (cites: Unicode UAX #9 §4 C1) (quote: "display all visible representations of characters in the order described by Section 3") [SHALL]
39. HIGHER_LEVEL_PROTOCOL_RESTRICTED — any simplification/shortcut of the algorithm (e.g. the no-explicit-formatting fast path) must remain one of the permitted higher-level protocols, i.e. equivalent to the full algorithm's result. (cites: Unicode UAX #9 §4 C2) (quote: "The only permissible higher-level protocols are those listed in Section 4.3") [SHALL]
40. BIDI_CLASS_ASSIGNMENT — classify each character by its Unicode Bidi_Class property (R/AL as strong RTL; WS/ON/CS/EN/ES/ET/NSM as neutral/weak), driving all later resolution. (cites: Unicode UAX #9 §3.2 BD1) (quote: "find the first character of type L, AL, or R while skipping over") [SHALL]
41. PARAGRAPH_LEVEL_FROM_FIRST_STRONG — derive base direction from the first strong (L/AL/R) character, defaulting the embedding level correctly when none is present. (cites: Unicode UAX #9 §3.3.1 P2/P3) (quote: "set the paragraph embedding level to one; otherwise, set it to zero") [SHALL]
42. WEAK_NUMBER_RESOLUTION — resolve European/Arabic numbers relative to the preceding strong type before reordering (the `:weak_number` handling citing W2). (cites: Unicode UAX #9 §3.3.4 W2) (quote: "If an AL is found, change the type of the European number to Arabic number") [SHALL]
43. NEUTRAL_DIRECTION_RESOLUTION — neutral characters take the direction of surrounding strong text, and otherwise the embedding direction (the neutral-attachment logic in `unbidify`). (cites: Unicode UAX #9 §3.3.5 N1/N2) (quote: "Any remaining NIs take the embedding direction") [SHALL]
44. IMPLICIT_LEVEL_RESOLUTION — assign implicit levels so numbers embedded in RTL runs are not visually reversed together with the surrounding strong RTL characters. (cites: Unicode UAX #9 §3.3.6 I1/I2) (quote: "A sequence of NIs takes the direction of the surrounding strong text") [SHALL]
45. REVERSE_LEVEL_RUNS — reorder by reversing contiguous runs from the highest level down to the lowest odd level (the RTL-span reversal in `unbidify`). (cites: Unicode UAX #9 §3.4 L2) (quote: "reverse any contiguous sequence of characters that are at that level or higher") [SHALL]
46. RESET_TRAILING_WHITESPACE_LEVEL — reset segment/paragraph separators and trailing whitespace to the paragraph level before reordering. (cites: Unicode UAX #9 §3.4 L1) (quote: "reset the embedding level of the following characters to the paragraph embedding level") [SHALL]
47. COMBINING_MARK_REORDER — keep combining marks correctly ordered relative to their base when a right-to-left run is reversed. (cites: Unicode UAX #9 §3.4 L3) (quote: "the ordering of the marks and the base character must be reversed") [MUST]
48. EXPLICIT_FORMATTING_CHARACTERS — account for explicit directional embedding/override/isolate and PDF/BN characters (remove/neutralize them per X9) so the simplification's "no explicit formatting characters" precondition holds and directional-override spoofing is not silently mis-skeletonized. (cites: Unicode UAX #9 §3.3.3 X9) (quote: "Remove all RLE, LRE, RLO, LRO, PDF, and BN characters") [SHALL]
