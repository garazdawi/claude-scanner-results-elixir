## Summary

`elixir_quote.erl` is pure quoted-AST construction/escaping with no deserialization, atom-table, filesystem, network, or crypto sinks; its one security-relevant surface is a data-controlled dynamic dispatch (`code:ensure_loaded` + `Module:'__escape__'`) reachable from the public `Macro.escape/2` when a caller passes a map with an attacker-controlled `__struct__` field.

## Security

#### `CSCAN-elixir_quote-macro-escape-struct-dispatch`

- **Finding ID** — `CSCAN-elixir_quote-macro-escape-struct-dispatch`
- **Severity** — Low
- **Confidence** — medium
- **Reachability** — unclear
- **CVSS** — `CVSS:3.1/AV:L/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N` — base 2.9 (Low)
- **Location** — `elixir_quote.erl:188-218` (`do_escape/2` map clause), specifically the dispatch at lines 194-203.
- **Class** — Code execution (data-controlled dynamic dispatch / gadget invocation).
- **Attack scenario** — A `compromised dependency` or `unauthenticated network peer` supplies a map to a `library consumer`'s application that performs metaprogramming with `Macro.escape/2` on runtime data (e.g. a code-generation, template, or config-to-AST helper). The attacker crafts `%{__struct__: SomeModule, ...}` where `SomeModule` is any atom. When the app calls `Macro.escape/2` on that map, this file runs `code:ensure_loaded(SomeModule)` (force-loading the module and any `on_load`) and, if `SomeModule` exports `__escape__/1`, invokes `SomeModule:'__escape__'(Map)` with the *entire attacker-shaped map* as argument. The attacker does not control the callback's body, only which module is dispatched to and the map handed to it. **New capability:** from merely "controls a data value," the attacker gains the ability to force-load an arbitrary already-on-path module and invoke that module's `__escape__/1` gadget with an attacker-shaped struct — a side-effecting dispatch out of an ostensibly pure data→AST transformation.
- **Trace** — `Macro.escape/2` → `elixir_quote:escape/3` (line 149) → `do_quote/2` (op `escape`/`escape_and_prune`, line 425) → `do_escape/2` map clause (line 188). The `maybe` block reads `__struct__` from the caller's map (line 190), takes the atom as `Module` (line 191), calls `code:ensure_loaded(Module)` (line 194) and `Module:'__escape__'(Map)` (line 203). `Module` originates entirely from the escaped term's `__struct__` key — i.e. from whatever data the caller forwards into `Macro.escape/2`.
- **Boundary** — Untrusted data value → compiler/metaprogramming API. `Macro.escape/2` is documented public API; its callers may forward attacker-influenced maps. The design implicitly trusts `__struct__` to denote a genuine struct created via `%Module{}`, but nothing verifies the map is a real struct of that module.
- **Impact** — Confidentiality: none directly. Integrity: an attacker-chosen module's `__escape__/1` runs with an attacker-shaped map; concrete effect is bounded by the gadget set (default stdlib exposes only `Regex`, whose `__escape__/1` recompiles the map's `source`/`opts` — see Validation). Availability: forced module loads (each is a one-time `code:ensure_loaded`; `on_load` side effects possible). Bounded: `__struct__` must already be an existing atom (no atom-table exhaustion), the module must be on the code path, and a non-existent/`__escape__`-less module falls through harmlessly to plain-map escaping; the returned AST is re-checked by `shallow_valid_ast` (invalid results raise), though gadget side effects have already occurred before that check.
- **Validation** — Ran (`elixir /tmp/escape_dispatch.exs`): `Macro.escape(%{__struct__: Gadget, evil: :payload})` invoked `Gadget.__escape__/1` — output `GADGET __escape__/1 WAS INVOKED with: %{__struct__: Gadget, evil: :payload}`; a gadget returning malformed AST was rejected (`BadGadget.__escape__/1 returned invalid AST`). Ran (`escape_tests.exs`): `Macro.escape(%{__struct__: :crypto, a: 1})` moved `:crypto` from `is_loaded => false` to loaded (`{false, {:file, ".../crypto.beam"}}`) — confirming the forced module load; non-existent `__struct__` and non-atom `__struct__` both fell through to `{:%{}, [], [...]}` with no crash. Ran (`regex_gadget.exs`): the default `Regex` gadget on `%{__struct__: Regex, source: "(a+)+$", ...}` returned an AST with a freshly-compiled `re_pattern`, confirming the gadget executes real logic on attacker data. This confirms the *mechanism*; whether a given deployment feeds untrusted `__struct__` maps to `Macro.escape/2` is caller-dependent (hence Reachability `unclear`).
- **Suggested fix** — Before dispatch, require the map to be a genuine struct whose keys match the module's declared struct (e.g. gate on `erlang:function_exported(Module, '__struct__', 0)` and compare `maps:keys(Map)` against `Module:'__struct__'()` keys), or restrict `code:ensure_loaded`/`__escape__` dispatch to modules already loaded at that point rather than force-loading arbitrary atoms. At minimum, document on `Macro.escape/2` that escaping untrusted maps can trigger module loads and `__escape__/1` callbacks.

## Risks / caveats

- **Caller-dependence is the crux.** This finding is Low precisely because reachability depends on out-of-file behaviour: an application must route attacker-influenced data into `Macro.escape/2` with an attacker-controlled `__struct__`. The mechanism is verified; the deployment pattern is not something this file can establish. If you know of consumers that `Macro.escape/2` deserialized/user maps, re-rate upward.
- **Default gadget set is tiny.** Only `Regex` exports `__escape__/1` in default stdlib (verified by enumeration), and its effect (regex recompilation) is not itself a strong amplifier. Applications that define their own structs with custom `__escape__/1` enlarge the gadget surface.
- The heavy Unicode/tokenizer obligations in the folder checklist (bidi, NFC, mixed-script, escape validation, UTF-8) **do not apply to this file** — `elixir_quote.erl` operates on already-parsed AST and terms, never on raw source bytes. No sub-claim from that checklist has a code path here.
- No `binary_to_term`, `*_to_atom`, `open_port`/`os:cmd`, `file:`/`filelib:`, network, crypto, NIF, ETS, or process-dictionary sinks exist in this file (grep-confirmed), so the always-flag and OTP secure-coding named-function classes are all vacuous here except the dispatch above.
