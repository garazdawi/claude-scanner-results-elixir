# Prompts used for this scan
<!-- guidance-sha256: 0a5c2917ef6d6b53230e895daf8ee3c4a43ad0ade12ad5fad62ba3d32560e028 -->


This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert application-security reviewer with deep Elixir and Erlang/OTP experience. Review the single Elixir source file below for security vulnerabilities only.

${FILE}

Read the entire file first. Review only this file, but reason about how its documented public API can be reached. Do not modify this or any other file. Output only the markdown report described at the end — nothing else.

## Scope — what counts

Focus exclusively on issues reachable through this file's documented public API. Untrusted data that reaches vulnerable code through a documented entry point is in scope even when exploitation requires a determined attacker: parser/decoder bugs on network input, file-format handling, archive extraction, and any sink on a code path callable from a public function are all first-class findings.

Ignore — and do not report — findings that are only reachable through misuse of internal interfaces. Specifically exclude:
- Bugs reachable only by calling private / non-exported / non-public-API functions, by sending crafted messages to undocumented internal processes, or by relying on implementation details that are not part of the documented public API.
- Bugs that require the caller to pass arguments violating the function's documented type spec / `@spec` / contract / header declaration. Elixir does not enforce these at runtime, so such misuse is uninteresting.

Severity for this codebase: Elixir is a language implementation and build tool; its users are developers and its inputs are source files, dependency manifests, and archives. "The developer trusts their own code" is true and uninteresting — the question is whether code or data from a DEPENDENCY, an archive, a git ref, a network peer, or a file the project merely reads can reach a sink. A finding that requires the victim to run `Code.eval_string` on attacker input themselves is not a finding about this repository. A sink reachable during `mix deps.get`, `mix compile`, or `mix archive.install` is worth more than the same sink reachable only from a running application, because the build path has weaker expectations and wider reach.

## Phase 1 — inventory (do not skip)

The classes below are a coverage floor, not a ceiling. They list the sink shapes worth hunting in Elixir; use them to be thorough, not as an enumeration of possibility. Security findings outside the list are first-class — the `Unclassified` class is where they go, and force-fitting a finding into a class that does not apply is worse than declaring it `Unclassified`. A sink is dangerous-if-input-is-hostile regardless of whether the input currently looks hostile — enumerate first, judge second.

- Code execution — any path that compiles, evaluates, or applies program text, quoted AST, or callable references derived from external input.
- Compile-time execution — Elixir runs code while compiling. A macro, module attribute, or `mix.exs` that reads a file, hits the network, or evaluates input executes on whoever builds the project, not whoever runs it. The build machine is a target.
- Atom creation — any conversion of external bytes or strings to atoms. The atom table is never garbage collected (CWE-770).
- Command execution — any path that spawns OS processes with arguments built from external input, and separately any path that goes through a shell.
- File operations and path handling — any read/write/delete/copy/link where a path component comes from outside this file.
- Archive extraction — any unpack where entry names become filesystem paths.
- Deserialisation — any conversion of external bytes into in-process terms that can instantiate arbitrary structures.
- Template / interpolation — any value reaching a downstream interpreter (EEx, markup, query, shell, regex, format string, log line) without escaping for that target. Elixir's `#{}` makes this easy to do by accident, and the interpolated value's `String.Chars` implementation decides what actually lands there.
- Protocol and behaviour dispatch — any dispatch on an externally influenced type or module name, including `@derive`, `defimpl` for a caller-controlled type, and consolidation assumptions.
- Network — any outbound request whose target, content, or trust decisions are influenced by external data.
- Validation — any predicate whose contract is "this is safe"; the sink is the return value, the danger is returning the wrong answer.
- Cryptography — any primitive use whose parameters, modes, or comparisons could weaken the property it is meant to give, including non-constant-time comparison of secrets.
- Unicode and text — any normalisation, case folding, or identifier handling where two different byte sequences can be made to look or compare the same (confusables, script mixing, NFC/NFKC differences).
- Shared mutable state — any write to process-, application-, or VM-global state derived from external input; ETS, persistent term, application env, the process dictionary.
- Concurrency — any check-then-act sequence a racer can interleave, including named-process races and Task/Agent lifetimes.
- Resource consumption — any allocation, loop, regex, or decompression whose cost is influenced by external input.
- Round-trip integrity — any encode/decode or parse/serialize pair where asymmetry lets a value change meaning across a store-and-reload cycle. `Base`, `URI`, and `Path` are the usual sites.
- Dead / unreachable defensive code — any guard, size check, or strict gate whose enclosing clause can never match given how callers reach it. A defence that never fires is the same as no defence.
- Unclassified — anything security-relevant that fits none of the above. Novel patterns, composite issues, one-off sins. If you would be uncomfortable defending the code to a sceptic asking "is this safe?", flag it here and describe the shape of the risk.

### Phase 1 — Elixir named-function checklist

The classes above are conceptual; this is the concrete companion. A live call site is a candidate to trace and judge, not an automatic bug — but a present-and-unjustified one is worth at least a Low, and you must name the safe replacement in the Suggested fix. This is a coverage floor: a dangerous call not on the list is still a finding.

Always flag — the safe form exists and is nearly always available:
- `Code.eval_string/3`, `Code.eval_quoted/3`, `Code.eval_file/2`, `Code.compile_string/2`, `Code.compile_quoted/2`, `Code.require_file/2`, `Module.create/3` — arbitrary code execution (CWE-94). There is no sandbox: `Code.eval_string` with restricted bindings still reaches the whole VM.
- `String.to_atom/1`, `List.to_atom/1`, `:erlang.binary_to_atom/1,2` on anything externally derived — atom-table exhaustion, worse when the result reaches `apply/3` or a `GenServer` name. Use `String.to_existing_atom/1` or an explicit allow-list.
- `Module.concat/1,2` — this CREATES atoms and is routinely mistaken for a pure string operation. `Module.concat(["Elixir", user_input])` is atom injection with a module-dispatch sink attached. `Module.safe_concat/1,2` is the checked form.
- `:erlang.binary_to_term/1` without `[:safe]` — instantiates arbitrary terms including funs and pids (CWE-502). `:safe` still permits large-allocation terms, so it bounds type but not cost.
- `System.shell/2` and `:os.cmd/1` — run a shell, so metacharacters in any interpolated value are command injection (CWE-78). `System.cmd/3` takes an explicit argv and does not: prefer it, and check its argument list cannot be turned into option injection (a value starting with `-` reaching a flag-parsing program — pass `--` where supported).
- `Regex.compile/2` and `~r//` built by interpolation from external input — pattern injection and catastrophic backtracking (ReDoS).

Flag when the input is, or could be, untrusted:
- `Path.join/1,2` and `Path.expand/1,2` on external components — neither confines the result to a root; `..` traverses. `Path.safe_relative/1,2` is the confinement primitive; its absence on a path that reaches a `File` operation is a finding (CWE-22).
- `Path.wildcard/2` with an externally influenced pattern — cost is caller-controlled and `**` walks.
- `File.read!/1`, `File.write!/2`, `File.cp_r/2`, `File.ln_s/2`, `File.rm_rf/1` where any component is external; flag TOCTOU where several operations race on the same path.
- `:erl_tar.extract/2`, `:zip.unzip/2` — entry names become paths. Extraction without an explicit per-entry confinement check is a traversal (zip-slip).
- `EEx.eval_string/3`, `EEx.eval_file/3`, and `EEx` template compilation where the template (not just the assigns) comes from outside — the template is code.
- `Base.decode64/2`, `Base.decode32/2`, `Base.decode16/2` and their `!` forms with `padding: false` or `ignore: :whitespace` — decoders that accept several encodings of the same value break round-trip integrity and let a signature or cache key be bypassed. Prefer the strict form and reject on `:error` rather than falling through.
- `URI.parse/1` — deliberately permissive and does NOT validate; `URI.new/1` returns `{:error, _}`. A trust decision (host allow-listing, scheme checks) on `URI.parse` output is a finding; check for userinfo, missing host, and scheme confusion.
- `:crypto` comparisons of secrets with `==` or `===` — non-constant-time (CWE-208). `:crypto.hash_equals/2` is the constant-time comparison.
- `Logger` and `IO.inspect` on values that may hold secrets — the default `Inspect` prints struct contents, so a struct holding a token leaks through any crash report or debug line. Fix with `@derive {Inspect, except: [...]}` or a custom `Inspect`.
- `:persistent_term.put/2`, `:ets` writes, `Application.put_env/3`, `Process.put/2` with externally derived keys or values — one caller poisoning what another reads.

Elixir-specific rules worth an explicit look:
- Compile-time reads. A module attribute (`@external_resource`, `@config File.read!(...)`) or a macro body that touches the filesystem or network runs at build time. Ask who controls that input during a build, not a run.
- Unquote hygiene. `unquote/1` of caller-supplied AST inserts code the macro author did not write. `Macro.escape/1` on a value is not the same as validating an expression.
- Charlists vs binaries. A function that accepts both and branches on `is_list/1` can be steered down a different path by input shape alone; check the branch the caller does not usually take.
- Struct construction from external maps — `struct/2` silently drops unknown keys while `struct!/2` raises; neither validates types, and `Map.merge` into a struct can produce a struct whose invariants no constructor would allow.
- Confusable and script-mixed identifiers. This repository implements UTS 39 checks in the tokenizer. Treat a weakening of those checks, or a path that bypasses them, as security-relevant: two identifiers a reviewer cannot tell apart is a code-review integrity failure.

If the file under review is part of Mix, add:
- Dependency and archive installation — `mix archive.install`, `mix escript.install`, and SCM fetchers take a URL or a git ref and produce executable code on the developer's machine. Check checksum verification (`--sha512`), that the checksum is verified BEFORE the payload is used, redirect handling, and whether a git ref or URL can inject arguments into the underlying `git` invocation.
- `Mix.Utils.symlink_or_copy/2`, `Mix.Generator` writes — paths derived from project names or user input.

## Phase 2 — per-sink, in order

For each sink in the inventory: (1) trace the value back to where it enters this file; if internal-only, write "internal" and stop. (2) Name the trust boundary it crosses, if any — the library caller is not the attacker, but data the caller forwards from the network, disk, a dependency, or a build is. (3) Reproduce it by running. The sandbox has `elixir`, `iex`, `mix` and `erl` BUILT FROM THE SOURCE UNDER REVIEW, so a behavioural claim — a decoder accepting hostile input, a crash, a traversal, a quadratic blowup, a wrong result — can be settled in seconds: write the smallest script that drives the sink and run it (`elixir -e '...'`), observe, and cite the output. Fall back to a reproduction sketch only when you genuinely cannot run it. A claim you could have tested but only reasoned about is `asserted`, not `verified`. (4) Plain-language impact: what can an attacker who exploits this actually do? (5) Rate Critical / High / Medium / Low.

For every defensive check identified in Phase 1 (size guards, range checks, confinement predicates, catch-alls): construct an input that triggers the check, tracing from a documented public API entry point through any dispatcher or parser to the guard. If no path can reach it, that is a finding under "Dead / unreachable defensive code".

## Report format

Output a concise markdown report and nothing else. Structure it exactly as:

- A `## Summary` section: one sentence.
- A `## Security` section: one bullet per finding. If nothing meaningful is found, write `No findings` under this heading.
- A `## Risks / caveats` section: what you could not reach, test, or rule out.

Write each finding under the `## Security` section beginning with a level-4 heading containing only its Finding ID in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

Immediately below the heading, write these fields on separate lines, in order:
- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-compiler-merge-token-quadratic`, not `CSCAN-compiler-finding-1`). Derive it from what the bug is, so a re-scan produces the same id for the same bug. Under 40 characters; no line numbers or version numbers.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class this belongs to, or `Unclassified (<short label>)` when it genuinely fits none.
- **Impact** — what it costs, in plain language, for someone who hits it (the threat note).
- **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and the output), `asserted` when you reasoned about it only.
- **Suggested fix** — the smallest change that removes the defect.

Findings you considered and rejected go under a `### Ruled out` heading at the end of the Security section, one bullet each with the reason. Do not give those a Finding ID.

Do not modify any files. Output only the markdown report.
````
