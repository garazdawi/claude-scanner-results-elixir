Out of scope (developer trusts their own invocation). **Confidence: high.**

- **`Mix.Utils.parse_mfa(module)` in `parse_module/1` (line 687) — atom creation via module parsing.** `module` is the argv of `mix xref callers MODULE` (matched as `["callers", module]` at line 461). *Verified by reading `Mix.Utils.parse_mfa` (`lib/mix/utils.ex:215-250`):* it calls `Code.string_to_quoted(mfa)` — **parse, not eval** — then `quoted_to_mfa/quoted_to_m`. Note this DOES create atoms: `quoted_to_m` calls `Module.concat(aliases)` (utils.ex:241) and passes through atom literals from the parsed AST (utils.ex:244). So the helper *is* an atom-creating sink — but its only input here is a single developer-typed argv string in a single-shot CLI process, so there is no unbounded/attacker-driven atom-table growth. Not attacker-reachable. **Confidence: high** (neighbour read; input origin is argv, fixed inside `xref.ex`).

- **`read_manifest/1` → `:erlang.binary_to_term/1` without `:safe` (CWE-502).** *Verified by reading `Mix.Compilers.Elixir.read_manifest/1` (`lib/mix/compilers/elixir.ex:354-363`):* the unsafe sink is `manifest |> File.read!() |> :erlang.binary_to_term()` at **elixir.ex:356** (no `:safe` option), wrapped in `try/rescue _ -> {[], []}` with an `else` clause validating the `@manifest_vsn` tuple shape. The sink is genuinely in the neighbour, not in `xref.ex`; this file only calls the documented `read_manifest/1`. The `manifest` argument is built by `manifests/0` (xref.ex:1382-1399) as `Path.join(Mix.Project.manifest_path(), "compile.elixir")` — a first-party `_build/<env>/lib/<app>/.mix/compile.elixir` artifact. An attacker able to write there already has arbitrary `.beam` execution on the build machine, so no privilege boundary is crossed. Not externally reachable. **Confidence: high** (sink location and missing `:safe` confirmed by neighbour read; input origin fixed inside `xref.ex`). See caveat below on cross-file composition.

## Risks / caveats
- The source tree under review is not compiled in this sandbox (the available `/opt/elixir` is a separate Elixir install, not built from these sources), so `mix xref` could not be driven end-to-end. The no-findings conclusion rests on data-flow/reachability reading plus direct inspection of the three cross-file sinks, which is appropriate here because each finding-negating claim is "no external data reaches this sink," established by tracing input origins (all argv or the first-party manifest path) rather than by triggering behavior. No axis-based ruled-out entry was narrowed by neighbour-reading alone.
- Two genuinely dangerous primitives sit on paths this file drives — the unsafe `:erlang.binary_to_term` at `elixir.ex:356` and the dynamic `backend.debug_info` dispatch — but both are gated behind first-party `_build` artifacts. If another Mix code path (outside this file) ever caused a *dependency- or archive-supplied* `compile.elixir` manifest or `.beam` to be read through `read_manifest`/`:code.which` for the current app, the `binary_to_term` sink would become a deserialization RCE. That composition is not reachable from anything in `xref.ex` (which always constructs the manifest path from `Mix.Project.manifest_path()`) and belongs to a review of the manifest producer/consumer in `Mix.Compilers.Elixir`.
- I did not audit the internal graph/`:digraph` helpers for non-security correctness (e.g. potential `MatchError` in `out_stats_filter`/`in_stats_filter` on parallel edges, where `:digraph.edge(graph, {file, v})` assumes a single edge id equal to the vertex pair). Those would be first-party robustness issues, not attacker-reachable, and are outside the security scope.
