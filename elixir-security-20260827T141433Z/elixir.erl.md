## Security

`No findings`

None of the sinks in this file is a security defect reachable from a documented public API without falling into an explicitly out-of-scope class (eval-runs-code, operator-controlled config, or caller-contract violation). The Unicode source-text obligations from the standards checklist (BIDI/Trojan-Source rejection, NFC, mixed-script, escape validation) are **not implemented here**: `string_to_tokens/5` forwards raw bytes to `elixir_tokenizer:tokenize/4` (confirmed at `elixir_tokenizer.erl:127`), which is the sole sanitiser. This file is the caller, not the enforcer, so those clauses are satisfied elsewhere and produce no gap here.

## Risks / caveats

- **Eval is by design not a sandbox.** `erl_eval/3` (line 366) and `eval_external_handler/3`'s `apply/2,3` (lines 383–384) run arbitrary code. Callers of `Code.eval_quoted/2` etc. are contractually responsible for only evaluating trusted quoted forms; treating an untrusted AST as safe to eval is a caller bug, not a defect defended here.
- **Cross-file dependence.** The rulings for `string_to_tokens/5` and `tokens_to_quoted/3` depend on `elixir_tokenizer.erl` (raw-byte sanitiser: bidi/`?break`/NFC/mixed-script) and `elixir_parser` (assumes well-formed tokens) actually enforcing their invariants. Those files are the correct place to audit the Unicode obligations; this file cannot be responsible for them.
- **Escaping-fun context leak is acknowledged, cosmetic.** A closure created during eval that escapes and is invoked later reads a stale/absent `?elixir_eval_env` from the process dictionary (comment at lines 358–360). Consequence is a wrong file+line in a stacktrace bottom — no confidentiality/integrity/availability impact.
