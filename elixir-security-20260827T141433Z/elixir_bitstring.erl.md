# Security review — `elixir_bitstring.erl`

## Summary
The file is a compile-time AST→AST transformer for `<<>>` bitstrings with no atom-creation, deserialisation, file, or network sinks. Two robustness/diagnostic defects turn an intended clean compile diagnostic into an uncaught internal Erlang exception that aborts the compilation unit and discards accumulated diagnostics: (1) an `ArithmeticError` when a bitstring `unit` argument is a non-number literal, reachable from **plain source with no macro**; and (2) an `if_clause` error when a bitstring specifier **macro returns a malformed 3-tuple AST node**, reached because `unpack_specs/2:271` pattern-matches macro output with a two-branch `if` that assumes AST well-formedness. Both are reachable only by a party already compiling attacker-supplied Elixir (already compile-time code execution), so neither grants new capability; both defeat the module-level error-accumulation path the code otherwise implements.

The only hedge phrases remaining in the prior report are the two `asserted` ruled-out entries whose `Not examined` axes are *user-authored looping/executing macros* — an infinite loop or arbitrary compile-time code exec. Per the re-review rules, an axis I cannot push through to a crash-in-this-module stays on `Not examined`, and reading a neighbour module never clears it. I re-confirmed by execution that neither axis is a distinguishing single-step input in this file, so both entries **correctly remain `asserted`** rather than being upgraded or falsely marked `Not examined: none`. Every other dismissal is `verified` with `Not examined: none` on executed evidence, re-run below where load-bearing.

## Security findings

#### `CSCAN-elixir_bitstring-unit-arg-badarith`
- **Finding ID** — `CSCAN-elixir_bitstring-unit-arg-badarith`
- **Severity** — Low
- **Confidence** — high
- **Reachability** — reachable (re-reproduced by execution)
- **CVSS** — `CVSS:3.1/AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` → 3.3 (Low)
- **Location** — `elixir_bitstring.erl:382` (`number_size/2`, `Size * Unit`), reached via `build_spec/8:364` because `validate_spec_arg/6:307-309` records an error but does not stop the flow.
- **Class** — Validation gap (validation records error but the bad value still reaches an arithmetic sink → uncaught `ArithmeticError` / compiler crash).
- **Attack scenario** — A party compiling attacker-supplied Elixir writes a bitstring segment whose `unit` argument is a non-number literal — e.g. `<<0::size(8)-unit(:foo)>>`, `unit("x")` — inside a module function. `validate_spec_arg/6:307` detects the non-integer unit and emits the intended diagnostic ("unit in bitstring expects an integer as argument"), but because the segment is inside a tainted module the error is *accumulated* (`function_error` → `module_error` → `elixir_module:taint` returns `ok`) and expansion continues; `build_spec/8:363-364` then calls `number_size(8, :foo)`, evaluating `8 * :foo` and raising `badarith`. The uncaught exception propagates out of `elixir_bitstring:expand/5`, aborting that compilation unit with an internal `ArithmeticError` and discarding any other diagnostics error-accumulation was meant to collect. **New capability gained: essentially none — reaching bitstring expansion means the caller is already compiling their own Elixir; this merely converts a clean multi-error diagnostic into an internal crash.**
- **Trace** — `expand/5:14` → `expand/8:32` (`::` clause) → `expand_specs/7:177` → `expand_each_spec/6:220` accepts `unit` with a non-integer arg; `validate_spec_arg/6:307` records `{bad_unit_argument, :foo}` and returns `ok`, leaving `unit => :foo` in the spec map → `build_spec/8:363-364` → `number_size(Size=8, Unit=:foo):382` → `8 * :foo`.
- **Boundary** — Untrusted Elixir source → compiler front-end macro-expansion. Crossed only by code already being compiled, so it confers no new privilege.
- **Impact** — Confidentiality: none. Integrity: none. Availability: an uncaught `ArithmeticError` aborts the current compilation unit and defeats the error-accumulation path (other queued diagnostics for that unit are lost); bounded to the compiling process, which the triggering party already controls.
- **Validation** — Re-ran 2026-08-28 on `elixir 1.21.0-dev` (OTP 29): `Code.compile_string("defmodule A do def f(x), do: <<0::size(8)-unit(:foo), x::binary>> end")` prints the diagnostic `unit in bitstring expects an integer as argument, got: :foo` **and then** raises `ArithmeticError: bad argument in arithmetic expression` — accumulate-then-crash confirmed empirically (both the printed diagnostic and the crash observed in one run). Control: `<<0::size(:foo), ...>>` → `NO RAISE` (clean `CompileError`, expansion halts cleanly). This directly witnesses the accumulation semantics, independent of any cross-file reading of `elixir_errors`.
- **Suggested fix** — In `build_spec/8` (integer/float branch, 363) guard the arithmetic so `number_size/2` runs only when `is_integer(Unit)` (or `Unit == default`); add a `number_size/2` fallthrough returning a non-integer sentinel so an already-reported `bad_unit_argument` never reaches `Size * Unit`.
- **Evidence** — `read elixir_bitstring.erl:307-311,363-383`; `ran /opt/elixir/bin/elixir` (diagnostic+ArithmeticError, and clean control), 2026-08-28.

#### `CSCAN-elixir_bitstring-unpack-specs-if-clause`  *(Upgraded from hedged assumption in first pass)*
- **Finding ID** — `CSCAN-elixir_bitstring-unpack-specs-if-clause`
- **Severity** — Low
- **Confidence** — low
- **Reachability** — reachable (re-demonstrated by execution)
- **CVSS** — `CVSS:3.1/AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` → 3.3 (Low)
- **Location** — `elixir_bitstring.erl:271` (`unpack_specs/2`, `if is_atom(Args) -> nil; is_list(Args) -> Args end`), reached from the macro-expansion re-entry at `expand_each_spec/6:253` (`unpack_specs(NewTypes, []) ++ T`).
- **Class** — Validation gap / unchecked AST shape from macro output (partial `if` with no fallthrough → uncaught `if_clause` error).
- **Attack scenario** — A bitstring specifier resolves to a **local (imported) macro** whose return value is a malformed AST node `{Atom, Meta, X}` where `X` is neither a list nor an atom (e.g. an integer). Example: `defmacro bad, do: {:foo, [], 123}`, used as `<<x::bad>>`. At `expand_each_spec/6:247` the unknown bittype `bad` is passed to `'Elixir.Macro':expand/2`, which returns the macro body `{:foo, [], 123}`; line 253 then calls `unpack_specs({:foo, [], 123}, [])`, matching the `{Expr, Meta, Args}` clause at line 270 with `Args = 123`. The `if` at line 271 has only `is_atom(Args)` and `is_list(Args)` branches, so `123` matches neither and raises an uncaught `if_clause` error that propagates out of `expand/5`, aborting compilation with an internal Erlang error instead of an `undefined_bittype`/malformed-AST diagnostic. The gap: `unpack_specs/2` treats macro output — an untrusted-shape value at the "macro result → assumed-well-formed AST" boundary — as guaranteed well-formed.
- **Trace** — `expand/5:14` → `expand/8:32` → `expand_specs/7:185` → `expand_each_spec/6:220` (`bad` unknown → `validate_spec` returns `none`, line 239) → `Macro.expand` at :247 returns `{:foo, [], 123}` ≠ `HA` → :253 `unpack_specs({:foo,[],123}, [])` → :270 clause, `Args=123` → :271 `if_clause`.
- **Boundary** — Untrusted Elixir source (via a macro) → compiler front-end. As with the badarith finding, reaching macro expansion already implies compile-time code execution, so no new privilege is conferred; the distinguishing defect is that the crash occurs in `elixir_bitstring`'s **own** partial function rather than in user code, defeating clean error reporting.
- **Impact** — Availability only: uncaught `if_clause` aborts the current compilation unit and discards accumulated diagnostics; bounded to the compiling process. A well-behaved-but-buggy macro (or a macro fed adversarial input by an otherwise-benign caller) can trigger it, so it is a genuine robustness gap even though a deliberately malicious author already controls the compiler.
- **Validation** — Re-ran 2026-08-28: precompiled `defmodule M do defmacro bad, do: {:foo, [], 123} end`, then `Code.compile_string("defmodule U do\n import M\n def f(x), do: <<x::bad>>\nend")`. Result `ErlangError: :if_clause`, re-captured stacktrace:
  ```
  src/elixir_bitstring.erl:271: :elixir_bitstring.unpack_specs/2
  src/elixir_bitstring.erl:253: :elixir_bitstring.expand_each_spec/6
  src/elixir_bitstring.erl:185: :elixir_bitstring.expand_specs/7
  src/elixir_bitstring.erl:48:  :elixir_bitstring.expand/8
  src/elixir_bitstring.erl:25:  :elixir_bitstring.expand/5
  ```
  Control cases (first pass, unchanged): a macro returning `[{:foo,[],123}]` (list-wrapped) does **not** crash — it falls to `unpack_specs/2:273` then `expand_each_spec/6:256` and produces a clean `undefined_bittype`; a remote macro call (`M.bad`) is not expanded here and yields a clean `undefined_bittype`. Only the bare-atom malformed 3-tuple from a local macro reaches the crash.
- **Confidence rationale (low)** — Reachability is certain (executed twice, same stacktrace). Confidence held low because severity/scope is debatable: triggering requires authoring or invoking a macro, which is itself compile-time code execution; a determined attacker in that position can already crash the compiler. Filed rather than ruled out because it is exactly parallel to the accepted badarith finding — an internal partial-function crash where a graceful diagnostic was intended — and the first-pass dismissal rested on the untried macro-output axis, now tried.
- **Suggested fix** — Give `unpack_specs/2:271` a total mapping: add an `else`/fallthrough branch (treat a non-list/non-atom `Args` as `nil`, or emit an `undefined_bittype`/malformed-spec diagnostic) so malformed macro output is reported cleanly instead of raising `if_clause`.
- **Evidence** — `read elixir_bitstring.erl:220-274`; `ran /opt/elixir/bin/elixir` (crash + stacktrace at :271 re-captured 2026-08-28; control cases from first pass).

## Risks / caveats
- Both findings are Low: the compiler front-end only processes source a party is already compiling, so a crash grants no capability beyond the compile-time code execution compilation already implies. They are nonetheless real uncaught-exception bugs the Elixir team would want to fix, since `validate_spec_arg` and `unpack_specs` both clearly *intend* graceful rejection.
- The badarith finding's accumulate-then-crash semantics are witnessed **directly by execution** (diagnostic printed *and* crash reached in the same run; control halts cleanly). No finding rests on an unverified cross-file assumption about `elixir_errors`.

### Ruled out
- **`number_size/2:382` big-integer multiply DoS** — Reason: `Size*Unit` on huge literal integers is a bignum multiply, effectively O(1); no amplification. Axes examined: integer width, sign, radix | Not examined: none. Basis: verified (read 130,381-383; large-literal multiply is trivial).
- **`compute_alignment/3:130` `Size*Unit`** — Reason: guarded by `is_integer(Size), is_integer(Unit)`; a non-integer unit falls to `_,_,_ -> unknown` (empirically no crash — the `unit(:foo)` run passed through the alignment path without raising there; only `number_size/2` crashed). Axes examined: non-integer unit (atom/tuple/binary), default | Not examined: none. Basis: verified (read 130-148; run 2026-08-28).
- **`concat_or_prepend_bitstring/6:107` `{alignment, Alignment} = lists:keyfind(...)` badmatch** — Reason: every expanded `<<>>` gets `{alignment, _}` prepended to its meta by `expand/5` (lines 20 and 27, confirmed on re-read), so `keyfind` on `PartsMeta` always returns a tuple, never `false`; a non-integer/`unknown` alignment takes the `else` branch (114-115), not a badmatch. Axes examined: nested-binary concat, `unknown` alignment, integer alignment | Not examined: none. Basis: verified (read 20,27,88,105-121; nested-concat run → no exception).
- **`'Elixir.Macro':expand/2:247` (code execution)** — Reason: compile-time macro expansion runs arbitrary code by design; reaching it means the caller is already compiling untrusted code (documented as running code, not a sandbox). Axes examined: unknown-bittype dispatch to Macro.expand, fixpoint termination | Not examined: mutually-recursive user macros (= user code exec; not an axis this folder defends per the threat model). Basis: asserted. Depends on: threat model — compilation executes code by contract; macro exec is not a boundary this folder defends. *Re-review note: the `Not examined` axis is user-authored code execution; it cannot be pushed through to a distinguishing crash-in-this-module, and reading `elixir_expand`/`elixir_dispatch` would not clear it. Stays `asserted`.*
- **`expand_each_spec/6:253` recursion / infinite loop** — Reason: for a fixed parsed `-`/`*` spec tree the depth is bounded; an unbounded loop requires mutually-recursive user macros expanding to each other forever, i.e. compile-time code execution the attacker already has, indistinguishable from ordinary macro non-termination (not guarded anywhere in the expander). Distinct from the `unpack_specs` if_clause finding, which is a single-step crash in this module's own code, not a user-macro loop. Axes examined: `-`/`*` nesting depth, single macro expansion (ran) | Not examined: recursive macro pairs (out of scope; an infinite loop, not a distinguishing input). Basis: asserted. Depends on: `elixir_parser.yrl` bounds parsed-spec nesting; `'Elixir.Macro':expand` is a fixpoint for non-recursive macros. *Re-review note: same as above — the untried axis is a non-terminating user program, not an input I can run to a crash here. Stays `asserted`.*
- **`expand_spec_arg`/`expand_match`/`expand_expr` → `elixir_expand:expand`** — Reason: plain delegation to the standard expander; introduces no new sink in this file (variable-scope juggling around `prematch`/`reset_read` only, via `elixir_env:reset_read`/`prepare_write`/`close_write`). Axes examined: full-file grep for atom-creation sinks | Not examined: none. Basis: verified (read whole file; no atomising call present).
- **`type/4:216`, `validate_expr/3:164`, `validate_size_required/6:313`, `concat_or_prepend_bitstring` unsized/unaligned checks** — Reason: validation predicates that emit clean compile errors; a wrong answer only defers/relaxes a compile-time rejection of the compiler-invoker's own code, granting no cross-context capability.
