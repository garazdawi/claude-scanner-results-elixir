## Summary

`elixir_parser.yrl` is the yecc grammar for the Elixir compiler front-end (reached from the documented public API `Code.string_to_quoted/2` → `:elixir.string_to_quoted/5` → `tokens_to_quoted` → `elixir_parser:parse/1`). Its reduce actions are robust against crashes on grammar-valid tokens, and the alias-chain builder appends to a growing list once per segment — an unconditional O(n²) parse-time blowup that a supplier of untrusted source can exploit for CPU denial-of-service (re-reproduced this pass). A second, low-confidence concern remains: `tokens_to_quoted` wraps the parse in a **catch-less** `try…of…after` (elixir.erl:467-479), so any reduce action that raised a non-`throw` `error:`/`exit:` exception would escape as a raise rather than a clean `{error,_}` tuple; I examined the concrete conversion sinks (notably `binary_to_existing_atom`) and found them safe, but could not exhaustively fuzz every token stream, so I surface the residual explicitly.

## Security

#### `CSCAN-elixir_parser-alias-chain-quadratic`

- **Finding ID** — `CSCAN-elixir_parser-alias-chain-quadratic`
- **Severity** — Medium
- **Confidence** — high
- **Reachability** — reachable
- **CVSS** — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` → 5.3 (Medium). (A:L scores a single exploitation, tying up one parsing process for tens of seconds to minutes; a service that fans out unbounded concurrent parses of untrusted source trends toward A:H / 7.5.)
- **Location** — `elixir_parser.yrl:880`, `build_dot_alias/3` (grammar rule `dot_alias -> matched_expr dot_op alias` at `elixir_parser.yrl:481`).
- **Class** — Resource consumption (algorithmic complexity, CWE-407).
- **Attack scenario** — An attacker who can hand untrusted Elixir *source text* to a host that parses it — a formatter/`mix format` run over a contributed file, a language server opening an attacker-authored buffer, an online playground, a doc/markdown tool, or any service calling `Code.string_to_quoted/2` on user data (all explicitly in this folder's threat model) — submits a single long alias expression `A.A.A.…A` of a few hundred KB. Each `.A` segment forces one more `Left ++ [Right]` over an ever-growing accumulator, so parse cost grows as the square of the segment count while the resulting AST is only linear in size. The victim is the operator of the parsing service; no authentication or privilege is required beyond the ability to submit source. For the many in-scope tools that *parse but do not execute* the source (formatters, LSPs, analyzers, doc extractors), the attacker gains an asymmetric CPU-exhaustion primitive — a small upload consumes minutes of a core — that they do not otherwise have, since parsing alone grants no code execution.
- **Trace** — `Code.string_to_quoted/2` → `:elixir.string_to_quoted/5` → `:elixir.tokens_to_quoted/3` (`elixir.erl:464`) → `elixir_parser:parse/1`. For `A.A.…A`, `dot_op` is left-associative, so the chain reduces as `((A.A).A)…`; each reduction hits `build_dot_alias(_Dot, {'__aliases__', Meta, Left}, {'alias', _, Right})` and returns `{'__aliases__', _, Left ++ [Right]}` (`elixir_parser.yrl:874-880`). `Left ++ [Right]` copies the whole left list, so N segments cost 1+2+…+(N-1) = Θ(N²) conses. No source-size or alias-depth cap exists upstream: I re-read `elixir.erl:464-479` this pass — `tokens_to_quoted/3` calls `put_parsing_state(Opts)` then `elixir_parser:parse(Tokens)` inside `try…of…after` with no length guard.
- **Boundary** — Untrusted source text crossing into the compiler front-end via a documented public parse API.
- **Impact** — Confidentiality: none. Integrity: none. Availability: super-linear CPU/allocation in the parsing process; a ~256 KB expression already costs ~24 s, ~1 MB extrapolates to ~6 min of single-core time, and repeated submissions saturate all cores. Bounded to the caller's process.
- **Validation (this pass, fresh runs)** —
  - Re-compiled this exact `.yrl` with `yecc` + `erlc` and drove the alias path with hand-built tokens (`{alias,{1,C,nil},'A'}` / `{'.',{1,C,nil}}`), process dict set to `columns=false, token_metadata=false, literal_encoder=false, warnings=[]`:\
    `ran erl -noshell -pa . -eval 'drive:go()'` → `N=8000 75.02 ms`, `N=16000 367.09 ms`, `N=32000 1603.81 ms`, `N=64000 5881.66 ms`, all `segs=N`. Each N-doubling ≈4×'s the time — the O(n²) signature; `segs=N` confirms a single flat `__aliases__` node built by repeated single-element appends.
  - Prior-pass end-to-end through the real tokenizer+parser (`Code.string_to_quoted/2`, Elixir 1.21.0-dev): `n=128000 bytes=255999 24264.1 ms segs=128000` — consistent with the fresh direct-token curve.
  - The quadratic is unique to this path: every other list accumulator in the file prepends and `reverse/1`s once (`container_args_base`, `call_args_no_parens_comma_expr`, `kw_base`, `assoc_base`), i.e. linear; only `build_dot_alias` appends to the end.
- **Suggested fix** — Accumulate segments in reverse (keep `[Right | Left]`) and `lists:reverse/1` once when the `__aliases__` node is finalized, or thread a difference-list accumulator so the whole chain is O(n). The `lists:keystore(last, 1, Meta, …)` on `elixir_parser.yrl:877` is O(1) and can stay.
- **Evidence** —
  - `read elixir_parser.yrl:481,874-880` — rule and `Left ++ [Right]` (still present, unchanged).
  - `read elixir.erl:464-479` — public entry `tokens_to_quoted/3`; catch-less `try…of…after`; no size cap.
  - `ran erl -noshell -pa . -eval 'drive:go()'` — `N=64000 5881.66 ms segs=64000` (this pass).

#### `CSCAN-elixir_parser-uncaught-reduce-exception` — **Upgraded from hedged assumption in first pass**

- **Finding ID** — `CSCAN-elixir_parser-uncaught-reduce-exception`
- **Severity** — Low
- **Confidence** — low
- **Reachability** — unproven (no token stream reproduced that triggers it; the concrete conversion sinks I examined are safe)
- **CVSS** — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:L` → 3.7 (Low). AC:H because no known input reaches it; A:L because the blast radius is the single parsing process.
- **Location** — reduce actions in `elixir_parser.yrl` (all `build_*`/`collect_stab`/`check_stab`/`extract_identifier`/`build_quoted_atom` clauses), consumed by the catch-less `try elixir_parser:parse(Tokens) of … after …` at `elixir.erl:467-479`.
- **Class** — Improper exception handling / availability (CWE-248).
- **Why this is upgraded, not dismissed** — The first pass rated the "no reduce action raises an uncaught `error:`" claim as `asserted` ("Sampled, not exhaustive") — the exact hedge flagged. Because "exhaustive fuzzing of all token streams" is not a triable axis (I cannot enumerate every token stream), I cannot promote it to `verified`; per the re-review rule I surface the unverifiable residual as a low-confidence finding so a later pass re-examines it, rather than leaving it as a confident dismissal.
- **What I *did* verify this pass (executed, cross-implementation)** —
  - The most concrete parse-time raise sink is `build_quoted_atom(..., Safe, ...)` → `erlang:binary_to_existing_atom(H, utf8)` (clause 1, `elixir_parser.yrl:1034-1036`), which raises `error:badarg` (not a `throw`) on a non-existing atom and would escape the catch-less `try`. I traced the token provenance in `elixir_tokenizer.erl`: `atom_safe`/`kw_identifier_safe` (the only `Safe=true` producers, `:298,:568-569`) are emitted **only** in the `{ok, Unescaped}` multi-part branch (`elixir_tokenizer.erl:562-568`, `:858-864`); the single-binary literal case (`:552`, `:849`) is resolved inside the tokenizer by `unsafe_to_atom`, whose `existing_atoms_only=true` clause wraps `binary_to_existing_atom` in a `try/catch` returning `{error, "unsafe atom does not exist: …"}` (`elixir_tokenizer.erl:1108-1122`). So an `atom_safe` token always carries a multi-part `Args`, which hits `build_quoted_atom` clause 2 (`:1037-1044`) — a **runtime** AST node, never the parse-time `binary_to_existing_atom`.
  - Executed proof: `ran /opt/elixir/bin/elixir` driving `:elixir.string_to_quoted/5` with `existing_atoms_only: true` on fresh (guaranteed-non-existing) atoms — literal `:"zzz_fresh_atom_a1"`, interpolated `:"zzz_fresh#{1}atom_a2"`, keyword `["zzz_fresh#{1}kw_a3": 1]`. All three returned `{:error, {…, "unsafe atom does not exist: ", …}}`. None raised. This exercises the tokenizer's `existing_atoms_only` `binary_to_existing_atom` path and the parser's build path for the same input — the axis is tried through both implementations, and they agree (clean error tuple, no escape).
- **Residual concern** — I have not proven that *no* grammar-reachable token stream drives some *other* reduce action to a non-`throw` `error:`/`exit:` (e.g. an unanticipated `function_clause` on a partial pattern, or a `characters_to_list` conversion raise on a caller-`literal_encoder`-derived `Reason`). The prior-pass ~35-input adversarial batch and the structural edge-proofs (below, retained) found none, but that is sampling. If such an input exists, the catch-less `try…of…after` would surface it as a raise to the caller of `Code.string_to_quoted/2` instead of the documented `{:error, _}` tuple — a robustness/availability defect for tools that expect a total function.
- **Suggested action** — Either confirm by fuzzing that the parser is total over the tokenizer's output alphabet, or add a defensive `catch error:_ / exit:_` arm in `elixir.erl` `tokens_to_quoted/3` that converts unexpected exceptions into a `{error, _}` tuple (the `after` already handles cleanup).
- **Evidence** —
  - `read elixir.erl:467-479` — catch-less `try…of…after` (only matches `{ok,_}`/`{error,_}` in the `of`).
  - `read elixir_parser.yrl:1034-1047` + `elixir_tokenizer.erl:552-568,849-864,1108-1122` — `Safe=true` never reaches parse-time `binary_to_existing_atom`.
  - `ran /opt/elixir/bin/elixir` — three fresh-atom `existing_atoms_only` inputs → clean `{:error,_}`, no raise.

## Risks / caveats

- **Unicode obligations do not apply to this file.** The folder's BIDI/NFC/mixed-script/escape-validation checklist (UAX #31/#9/#15, UTS #39/#55) is enforced in `elixir_tokenizer.erl`/`elixir_interpolation.erl`, which sanitise raw bytes *before* tokens reach this grammar. `elixir_parser.yrl` consumes already-well-formed tokens and performs no codepoint-level identifier handling, so none of those sub-claims are checkable here; I did not force a match.
- **Cross-file dependency (verified this pass).** The alias finding relies on the tokenizer emitting no cap on alias-chain length (confirmed end-to-end prior pass: 128 000 segments tokenized+parsed) and on `elixir.erl:464-479` imposing no default source-size limit (re-read this pass: none). If a caller wraps parsing behind its own input-size guard, the DoS is bounded accordingly.
- **Atom creation is inherent, not a new sink.** `build_quoted_atom/3` calls `binary_to_atom(H, utf8)` for `Safe=false` quoted-atom literals; this is the required semantics of an atom literal and matches the threat model's acknowledged, out-of-scope "atom exhaustion via source" property — it adds no surface beyond what the tokenizer already atomises for every identifier. (The `Safe=true`/`binary_to_existing_atom` variant is examined under the low-confidence finding above and does not raise at parse time.)
