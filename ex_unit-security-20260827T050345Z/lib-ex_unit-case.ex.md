## Summary

`ExUnit.Case` is compile-time test-registration machinery (the `use ExUnit.Case`, `test`, `describe` macros plus the `register_test/6` and `register_*_attribute/3` helpers that manipulate module attributes while a test module compiles). Its only inputs are the developer's own test source, `use`-options, tags, and the arguments third-party macro authors pass to `register_test/6`; there is no network, file, deserialization, shell, path, or `Code.eval` surface, and the single atom-creation sink is length-bounded and defensively wrapped, so I found no meaningful security defects.

## Security

No findings.

### Ruled out

- **`String.to_unsafe_atom/1` in `build_test_name/1` (line 929) — atom-table growth (CWE-770).** This is the only atom-creation sink. Its input is `description` (`"#{test_type} #{name}"`), assembled in `register_test/6` from the `test_type`/`name` supplied by the `test`/`describe` macros or a third-party macro author — all developer/compile-time controlled. The name is hard-bounded: `build_test_name/1` truncates anything `> 255` bytes to `≤ 254` bytes before conversion (verified: 255 ASCII bytes → valid atom; 256 → `SystemLimitError`, which is the path the truncation prevents and which is additionally rescued at lines 930-937). The count of atoms created is bounded by the number of tests/doctests in the source. Even the strongest reachable vector — `doctest SomeDependencyModule` pulling names from a dependency's docstrings — grants no capability a malicious dependency lacks, since a dependency already executes arbitrary code (its own macros / `mix.exs`) at build time. Self-inflicted and out of scope per the folder threat model.
- **`build_test_name/1` truncation feeding invalid UTF-8 to `to_unsafe_atom` → uncaught `ArgumentError`.** I hypothesized that `String.byte_slice(name, 0, 246)` (line 924) could split a multi-byte character, yielding invalid UTF-8 that raises `ArgumentError` (not the rescued `SystemLimitError`). Verified false: `String.byte_slice/3` aligns to codepoint boundaries — slicing a 405-byte emoji string at offset 246 returned 245 bytes of **valid** UTF-8, and `build_test_name` produced a clean atom. The `ArgumentError`-on-invalid-UTF-8 path is not reachable through this truncation.
- **`IO.warn`/`inspect` at lines 382, 433-437, and the `raise` messages.** All use `inspect/1` on developer-supplied options/patterns; no interpolation reaches a downstream interpreter (no format string, log-forwarding, or markup sink). Not a template/interpolation defect.
- **Dynamic dispatch `module.__ex_unit__(:config)` in `__after_compile__/2` (line 653).** `module` is the module currently being compiled, not externally influenced; the dispatched function is generated by `__before_compile__` in the same file. No untrusted type/module-name crosses this call.
- **`IEx.Pry.annotate_quoted/3` in `annotate_test/1` (line 484).** Gated on the `:ex_unit`/`:breakpoints` application-env flag (developer/tooling config) and operates on the test body AST written by the developer. No external-input boundary.
- **`register_attribute/3` & siblings (lines 776, 821, 861).** The attribute `name` is constrained to an atom by `is_atom(name)` guards — the caller passes an existing atom; no string→atom conversion occurs here.

## Risks / caveats

- I treated `register_test/6` as documented public API and assumed its callers (including `ExUnit.DocTest`, in a separate file) forward only developer- or dependency-authored names; I did not audit those call sites here. Since the sink is length-bounded and equivalent to capabilities a malicious dependency already holds at build time, this does not change the conclusion.
- All behavior in this file runs at **compile time** on the build machine. The assessment rests on the folder threat model's premise that test source, docstrings, and `use`-options originate from a trusted local developer (or a dependency, which already has build-time code execution). If a workflow were to route genuinely untrusted, unbounded strings into `register_test/6`'s `name` from outside a normal build, the bounded atom growth there would be the only thing to re-examine — and it is capped at 255-byte atoms, one per registered test.
- Reproductions were run against the in-tree Elixir 1.21.0-dev / OTP 29 build; `String.byte_slice/3` codepoint-boundary alignment is the load-bearing behavior and was confirmed empirically.
