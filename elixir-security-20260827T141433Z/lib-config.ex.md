# Security review — `Config` (`lib/elixir/lib/config.ex`)

## Summary
`Config` is a build-/boot-time configuration DSL whose one powerful sink — `Code.eval_string` — is the documented purpose of the module (config files *are* Elixir code), and its data-taking public API (`config/2,3`, `read_config/1`) is atom-guarded with no dangerous sinks, so no security issue is reachable with untrusted data through the documented public API. In this pass I read the two callgraph neighbours the first pass hedged about — `Config.Reader` (`lib/config/reader.ex`) and `Config.Provider` (`lib/config/provider.ex`) — and executed the integration path (`Config.Reader.eval!` → `Config.__eval__!` → `Code.eval_string`) to convert the "outside this file" assumption into a verified trust-boundary statement. No findings.

## Security

`No findings`

I inventoried every sink in the file (`Code.eval_string`, `File.read!`, `Path.expand`, process-dictionary writes, `Keyword.merge`/`deep_merge` recursion, `inspect` in error strings) and traced each back to its entry point, including the `@doc false` integration surface reached from `Config.Reader`/`Config.Provider`. Every dangerous one is either fed exclusively by trusted project/release source (config files) or is guarded so untrusted-shaped input cannot reach it. Details in *Ruled out*.

### Ruled out

- **`Code.eval_string(contents, [], file: file)` — arbitrary code execution (`import_config!/3`, line 365).** *Basis: verified + by-design.* This is the module's contract: config files (`config/config.exs`, `runtime.exs`, and any `import_config`'d file) are Elixir programs and are meant to be evaluated. I re-confirmed this end-to-end through the neighbour entry point: `Config.Reader.eval!("fake.exs", "...System.put_env(...)...", env: :prod)` returned `[app: [k: :v]]` **and** set the env var (`side_effect: "yes"`), proving `contents` is executed verbatim. The `contents`/`file` arguments originate from files the *project or release author* specifies (see `Config.Reader.read!/2` line 100–103, `eval!/3` line 78–81; provider registration in `Config.Provider` moduledoc lines 30–36, 86–92). No untrusted-data flow forces those arguments. A sink that requires evaluating trusted config code the developer wrote is not a finding about this repo.
- **Atom exhaustion via `config/2`, `config/3`, `read_config/1` (lines 156, 203, 231).** *Basis: verified.* All three are guarded `is_atom(root_key)` / `is_atom(key)`; there is no `String.to_atom`/`Module.concat` in the file. A non-atom key raises `FunctionClauseError` with no atom created. Untrusted strings cannot be converted to atoms here.
- **Path traversal / `File.read!` via `import_config/1` (lines 306, 314).** *Basis: verified + reasoned.* The `file` argument is a source-code expression the config *author* writes (`import_config "#{config_env()}.exs"`), expanded relative to the config file's own `__DIR__` (line 306). There is no framework-level flow of network/attacker data into that argument. Confirmed no additional caller of `__import__!/1` outside `import_config/1`; `Config.Reader` reaches the eval path via `__eval__!`, not `__import__!`.
- **Attacker-controlled *path* into `Config.Reader.read!`/provider `{:system, VAR, path}` — code execution (neighbour path).** *Basis: verified via neighbour read + by-design.* **Upgraded from hedged assumption in first pass** (was: "lives outside this file"). I read `Config.Reader` (`init/1` line 56, `load/2` line 67, `read!/2` line 100) and `Config.Provider` (`config_path` type lines 99–112). The provider path is either an absolute path the release author hard-codes or a `{:system, VAR, suffix}` tuple whose *suffix* is author-controlled and whose *prefix* comes from an OS environment variable (e.g. `RELEASE_ROOT`). An attacker who controls that environment variable already has process-level control of the booting release, so this is not a boundary the module defends; the config file it points at is operator-provisioned and evaluating it is the documented purpose. No path in `Config.Reader`/`Config.Provider` feeds `Code.eval_string` from network/request data. This is by-design config evaluation, now verified rather than assumed. *Confidence: high that no in-tree untrusted-data flow reaches the sink; residual is the operator/env trust boundary, which is explicitly out of scope.*
- **"Dependency `config/config.exs` is not evaluated" guarantee (moduledoc lines 46–49).** *Basis: documentation claim; enforcement not in this file.* This closes the malicious-dependency vector, but the *enforcement* lives in Mix's config loading (not in `config.ex` or in `Config.Reader`/`Config.Provider`, which I read). Within this folder, nothing auto-discovers or evaluates a dependency's config, so `config.ex` does not itself open that vector; I flag only that the guarantee is asserted here and enforced elsewhere (Mix), which I did not read. *Confidence: medium that the guarantee holds system-wide (Mix not examined); high that config.ex introduces no dependency-config auto-eval.*
- **Infinite-recursion / self-import DoS (`import_config!/3`, lines 356–358).** *Basis: verified.* The `file in current_imports` guard fires on direct/transitive cycles (a file importing itself raises `ArgumentError … recursively`). The residual gap — two distinct paths (e.g. symlinks) resolving to the same file bypassing the exact-string match — only yields a stack blow-up when the *trusted* config is adversarial, and a BEAM stack overflow raises rather than crashing the node; not a boundary crossing. *Confidence: high.*
- **Process-dictionary state corruption / leak across nested or failed eval (`__eval__!/3`, lines 324–342).** *Basis: verified.* `put_opts/put_config/put_imports` capture the prior values, and the `after` block restores-or-deletes them. Confirmed that (a) nested `import_config` restores `config_env()` across the boundary, and (b) after an eval that *raises*, `{Config, :config}` and `{Config, :imports}` are back to `nil`. The fixed module-tuple keys are not externally derived. Config evaluation is single-process/sequential per the neighbour callers (`read!`, `eval!`, `read_imports!` each do one `__eval__!`), so no concurrent-writer race. *Confidence: high.*
- **`inspect/1` in error messages (lines 158, 388–389, 394–395, 403–404).** *Basis: reasoned.* These render config values the author supplied, at config/build time, into the author's own error output — not a cross-trust-boundary secret leak. *Confidence: high.*
- **`deep_merge/3` unbounded recursion (lines 375–381).** *Basis: reasoned.* Recurses only when both sides are keyword lists; reaching pathological depth requires two deeply-nested *trusted* config trees keyed identically. Input is project config, not untrusted data. *Confidence: high.*
