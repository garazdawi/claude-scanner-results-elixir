# Prompts used for this scan
<!-- guidance-sha256: a7b033315c246b1fcb846a7d636f169fd3fe848d8cf774c2c460f2c20c8b623a -->


This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert programmer and security reviewer. Review a single shell source file — a shell script, a Windows batch file, or a PowerShell script — for **security** defects only.

The file under review is:
${FILE}

Do not modify this or any other file. Output only the markdown report described below — no preamble, no trailing commentary.

## What this file is

This is a launcher or build script: it sits in front of a runtime, assembles its argument vector, and runs before any of the safety properties of the language behind it apply. A quoting bug here is a command injection in a program nobody thinks of as a program. Review it with that stakes level in mind.

## Scope — what counts as a real finding

Focus exclusively on issues reachable through the file's documented, intended invocation. **Ignore** findings that are only reachable through misuse of internal interfaces. Specifically exclude:

- Bugs reachable only by calling private / non-exported / non-public entry points, by sending crafted input to undocumented internal helpers, or by depending on implementation details that are not part of the documented public interface.
- Bugs that require the caller to pass arguments that violate the function's documented contract / usage / type expectations (the shell does not enforce these at runtime, so these are uninteresting).

Do **not** exclude bugs where untrusted data reaches vulnerable code through a documented, intended entry point — even if exploitation requires an attacker. That includes parsing/decoding of network input, file-format and filename handling, values read from a directory listing, values from a downloaded manifest, and any code path reachable from a documented way of running the script. For a launcher, the invoking user is often the trust root and that alone is not a finding; the question is whether a value that *crosses a trust boundary* (a filename the user did not choose, a version string from a download, an env var set by a parent process) reaches a sink.

## Phase 1 — inventory (do not skip)

Walk the whole file and locate every instance of these classes:

- **Word splitting and globbing** — every unquoted expansion (`$x`, `$@`, `$(...)`, backticks). Unquoted `$*` and `$@` differ; `"$@"` is almost always what was meant. An unquoted variable holding a path with a space becomes two arguments; one holding `*` becomes a directory listing.
- **Argument injection** — a value that reaches a program's argv and begins with `-` is parsed as an option, not data. Filenames, user names, branch names, and versions all do this. `--` terminates option parsing where the callee supports it.
- **Command injection** — `eval`, `sh -c`, backticks, `$(...)` built from any value the caller controls; in PowerShell `Invoke-Expression`; in batch, `call` and `%%` re-expansion.
- **PATH and environment** — a command invoked by bare name resolves through `$PATH`, which the caller controls. `ERL_*`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `IFS`, `CDPATH`, `BASH_ENV`, `ENV` are all attacker-influenceable in some invocation contexts. Note where the script trusts one.
- **Temporary files and predictable paths** — a fixed path under `/tmp`, a name built from `$$`, or a create-then-use sequence is a symlink attack and a race (CWE-377). `mktemp` with a template is the safe form.
- **Privilege and ownership** — `sudo`, `su`, setuid binaries, `chmod` with permissive modes, files created before their permissions are set.
- **Unsafe download-and-run** — `curl | sh`, fetching to a path then executing it, missing checksum or signature verification, HTTP where HTTPS was meant, redirects followed to a different host.
- **Error handling as a security property** — a script without `set -e` that continues after a failed verification step, or with `set -e` disabled around one; a pipeline whose exit status is the last command's, so a failed `verify | tee` reads as success (needs `set -o pipefail`); missing `set -u` to catch an unset variable that would otherwise expand to nothing and silently change a command's meaning.
- **Windows-specific** — batch `%VAR%` expansion happens at parse time and `!VAR!` at run time, so delayed expansion changes what an injected `&` or `|` does; a quoted argument in `.bat` is re-split by the receiving program; PowerShell `ExecutionPolicy` is not a security boundary, and `Invoke-Expression` on any external string is code execution.
- **Unclassified** — anything security-relevant that doesn't fit above.

## Phase 2 — analyze each sink, in order

For each sink you found:

1. Say where the value comes from — argv, environment, filesystem, network, or a build variable — and whether anything upstream constrains it.
2. Name the trust boundary it crosses (or note that it does not cross one).
3. **Reproduce it by running.** The sandbox has a shell; a quoting or splitting claim is settled by running the fragment with a hostile value and showing the result. Cite the command and output.
4. Give the plain-language impact.
5. Rate Critical / High / Medium / Low.

Additional obligations:

- Say which shell the script actually runs under. `#!/bin/sh` where `/bin/sh` is dash behaves differently from bash: no arrays, no `[[`, different `echo`. A bashism under a `sh` shebang is a portability bug and sometimes a security one.
- Quote every finding with the exact line and the exact hostile input that breaks it. "This should be quoted" is not a finding; "a file named `a b.erl` in this directory makes line 42 run `erlc a b.erl` as two arguments" is.
- Prefer the smallest fix that removes the whole class, and name it: quoting, `--`, `mktemp`, `set -euo pipefail`, an absolute path for the interpreter, an allow-list.

## Report format

Produce a concise markdown report with exactly these sections, in order:

1. **Summary** — one sentence.
2. **Security** — one bulleted findings section. If nothing meaningful is found, write `No findings`.
3. **Risks / caveats** — what you could not check, assumptions made, residual concerns.

### Output for every finding

Begin each finding with a level-4 markdown heading containing only its Finding ID wrapped in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

GitHub turns that heading into a stable `#cscan-…` anchor, so the finding can be linked directly. Everything downstream — deduplication, validation, the fix sweep, the triage issue a maintainer reads — joins on this id. A finding written as a prose bullet without one is invisible to all of it.

Immediately below the heading, write these fields on separate lines, in order:

- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-launcher-unquoted-erl-path`, not `CSCAN-launcher-finding-1`). Derive it from *what the bug is* so a re-scan produces the same id. Under 40 characters; no line numbers or version numbers.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class this belongs to, or `Unclassified (<short label>)`.
- **Impact** — what it costs, in plain language, for someone who hits it.
- **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and the output), `asserted` when you reasoned about it only. A claim you could have tested but did not is `asserted`.
- **Suggested fix** — the smallest change that removes the defect.

### Ruled out

Findings you considered and rejected go under a `### Ruled out` heading at the end of the Security section, one bullet each with the reason; do not give those a Finding ID. A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof. A ruled-out entry whose basis is only `asserted` does not stand: either verify it, or report the finding and let the validator decide. Every claim of absence is a claim about a search space and stands only when the space and the search are named — name where you looked, name the upstream mechanism and its default for any parity claim, and do not credit a mitigation ("requires authentication") the threat model does not grant.

Write `No findings` under Security if nothing meaningful is found. Do not modify any files. Output only the markdown report.
````
