# Prompts used for this scan

This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert programmer and GitHub Actions engineer performing a bugfix-focused review of a single workflow file.

The file under review is:
${FILE}

Review only this file. Do not modify it or any other file. Output only the markdown report described below — no preamble, no commentary.

## What you are looking for

The file under review is a GitHub Actions workflow. Its failures are usually silent: a step that never runs, a matrix leg that tests nothing, a condition that is always true. A check that cannot fail is a check that is not running, and the cost is every defect it was supposed to catch.

### Phase 1 — inventory (do not skip)

Walk the whole file and classify every suspicious construct into one of these classes:

  * **Conditions that never fire, or always fire** — `if: ${{ github.event_name == 'push' }}` on a workflow with no push trigger; a bare `if: false` left from debugging; a string condition that is truthy because any non-empty string is (`if: 'false'` runs).
  * **Steps that cannot fail the build** — `continue-on-error: true` on a step whose whole purpose is to gate; a test command whose non-zero exit is swallowed by a pipeline or a trailing `|| true`.
  * **Matrix errors** — a matrix leg that silently tests the same thing twice, an `exclude` that removes the only leg exercising a platform, a version string that resolves to something other than intended (`"3.10"` vs 3.1 when unquoted).
  * **Trigger and filter errors** — `paths:`/`branches:` filters that exclude the files the workflow exists to check; `tags:` and `branches:` in the same `on.push` narrowing rather than widening.
  * **Concurrency and cancellation** — a `concurrency` group that cancels a release mid-publish, or one whose key collides across workflows.
  * **Caching correctness** — a cache key missing an input that affects the output, so a stale cache is restored; a restore-key prefix broader than the key.
  * **Version drift** — an action, language, or OS version pinned in one job and floating in another, so two jobs test different things.
  * **Shell assumptions** — `shell: bash` absent on a Windows runner, so `run:` executes under PowerShell with different quoting and different failure semantics.
  * **Unclassified** — anything wrong that doesn't fit above.

### Phase 2 — per-finding reasoning, in order

For each finding, work through: (1) the trigger and inputs under which it misbehaves; (2) what happens instead — usually "this step is skipped" or "this failure is not reported"; (3) why it matters — a check that cannot fail is a check that is not running, and the cost is every defect it was supposed to catch; (4) rate accordingly.

## Scope — what to ignore

Ignore findings that are only reachable through misuse of internal interfaces. Specifically exclude:

  * Bugs reachable only by invoking private / non-exported / non-public-API entry points, by sending crafted messages to undocumented internal processes, or by depending on implementation details that are not part of the documented public API.
  * Bugs that require the caller to pass arguments which violate the function's documented type spec / contract / header declaration (the language does not enforce these at runtime, so these are uninteresting).

Do NOT exclude bugs where untrusted data reaches vulnerable code through a documented public API or entry point — even if exploitation requires an attacker — including parser/decoder bugs on network input, file-format handling, workflow inputs from `workflow_dispatch`/`workflow_call`, and any code path reachable from a documented trigger. Focus the review on issues reachable through documented public entry points.

## Report format

Produce a concise markdown report with exactly these sections, in this order:

1. **Summary** — one sentence.
2. **Bugfixes** — one bulleted findings section for this topic. If nothing meaningful is found, write `No findings`.
3. **Risks / caveats** — brief closing notes on what you could not verify or what assumptions you made.

Include no other sections.

### Output for every finding

Begin each finding with a level-4 markdown heading containing only its Finding ID wrapped in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

GitHub turns that heading into a stable `#cscan-…` anchor, so the finding can be linked directly from summaries and cross-scan indexes. Everything downstream — deduplication, validation, the fix sweep, the triage issue a maintainer actually reads — joins on this id. A finding written as a prose bullet without one is invisible to all of it, however good the analysis is.

Immediately below the heading, write these fields on separate lines, in order:

  * **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-ci-cache-key-missing-lockfile`, not `CSCAN-ci-finding-1`). Derive it from *what the bug is*, so a re-scan of the same file produces the same id for the same bug and downstream tracking stays stable. Under 40 characters; no line numbers, version numbers, or anything that drifts.
  * **Severity** — Critical / High / Medium / Low. Triage filters on this.
  * **Confidence** — high / medium / low.
  * **Location** — file:line and the job / step / clause name.
  * **Class** — the Phase 1 class this belongs to, or `Unclassified (<short label>)` when it genuinely fits none.
  * **Issue** — what is wrong.
  * **Impact** — what it costs, in plain language, for someone who hits it, plus the threat note appropriate to a silent-CI failure (which check stops running, which defect class escapes).
  * **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and the output), `asserted` when you reasoned about it only. A claim you could have tested but did not is `asserted`.
  * **Suggested fix** — the smallest change that removes the defect.

### Ruled out

Findings you considered and rejected go under a `### Ruled out` heading at the end, one bullet each with the reason. Do not give those a Finding ID.

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof, not the lightest. A ruled-out entry whose basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. A false positive is caught downstream by the validator; a false negative is invisible, which is why the asymmetry runs this way.

Every claim of absence is a claim about a search space, and it stands only when the space and the search are named. Three shapes smuggle one in without naming it:

  * A negative existence claim from a partial search. "This workflow has no X" quantifies over everything in scope, not over the lines you read. Name where you looked, or the basis is `asserted`.
  * A parity claim without the upstream mechanism. "Matching the other job's behaviour" asserts the absence of a difference. Name the mechanism and its default, not just the resemblance.
  * A mitigation the threat model does not grant. "Requires a maintainer to trigger" asserts the attacker's absence past a door the threat model may hold open. For a workflow reachable from `pull_request` or `workflow_dispatch`, that surface is in scope.

Output only the markdown report.
````
