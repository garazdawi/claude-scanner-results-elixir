# Review: `elixir_erl_var.erl`

## Summary
No correctness, crash, or contract defects reachable through this module's documented compiler-internal API were found; the version-keying, name-generation, and binding round-trip logic are internally consistent.

## Bugfixes

No findings.

The file is small and self-contained (128 lines, no `-spec`s). I traced every export and its shared invariants:

- **`translate/4`** — anonymous `'_'` short-circuits; the named clause reads `{version, Version}` from `Meta` (always injected by the expander/`elixir_erl_pass` caller) and either reuses an existing `var_names` entry or delegates to `assign`. A missing `version` in `Meta` would `badmatch` at line 20, but `Meta` here is compiler-generated (never raw user source), so this is an internal contract, not a stray-input path.
- **`assign/2`** (line 28) — `Version = -(map_size(VarNames)+1)` yields a *fresh, strictly-more-negative* key on every call because `assign/4` grows the map by exactly one before the next `assign/2` can run. Positive versions come only from `Meta`; negative and positive spaces never collide, so no version aliasing / variable capture. Verified by tracing map growth across interleaved `assign/2` and `assign/4` calls.
- **`build/2` + `build_name/2`** (lines 39–49) — three disjoint erl-name namespaces coexist without collision: `"_N"` (anonymous, `build_name('_',_)`), `"_name@N"` (named), and `"_@N"` (`to_erl_var/1`, bindings). Confirmed by comparing the three `list_to_atom` formats.
- **`from_env/1,2`** (lines 53–70) — `to_erl_vars` assigns dense `0..N-1` counters; `counter=#{'_' => map_size(VarsMap)}` seeds the anonymous counter past the binding range, and the `"_N"` vs `"_@N"` format split keeps later `build('_',…)` names off the binding names.
- **`load_binding/2`** (lines 72–101) — the `Prune=true` tail injects one synthetic `{{elixir, prune_binding}, true}` pair then re-enters with `false`; `Normalized` is reversed once at the end (line 98), so order is preserved and there is no `Acc ++`/quadratic pattern. `load_pair/1` inverts `dump_binding`'s key reconstruction.
- **`dump_binding/4`** (lines 103–127) — the three fold clauses partition cleanly (`is_atom(Kind)` always holds for `ExVars` keys; the discriminator is `Version > PruneBefore orelse is_map_key(...)`, with `PruneBefore >= 0` gating removal and `PruneBefore < 0` disabling pruning). Kept vars stay in `V`; only unused pruned vars are removed. `Key` reconstruction (nil→`Var`, else→`Pair`) is the exact inverse of `load_pair/1`.

## Risks / caveats
- No `-spec`s are present in the file, so the "spec-totality checklist" is vacuous here; totality was assessed against actual clause coverage instead.
- Several dismissals rest on the invariant that `Meta` and the `#elixir_erl{}` / `#elixir_ex{}` records are compiler-generated by the in-folder callers (`elixir_erl_pass`, `elixir_erl_for`, `elixir_erl_try`, `elixir`, `elixir_compiler`) and always carry a `version` entry and well-formed `var_names`/`counter`/`vars`/`unused` maps. If a caller ever forwards raw user `Meta` lacking `version`, line 20 becomes a reachable `badmatch`; that is out of scope for the documented internal contract but is the single most fragile point.
- The `load_pair/1` `function_clause` on a non-2-tuple binding element is reachable only via a binding that violates the `Code.eval_*` keyword-list contract; excluded per scope rules.
