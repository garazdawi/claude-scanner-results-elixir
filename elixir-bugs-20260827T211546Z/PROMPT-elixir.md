# Prompts used for this scan

This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert Elixir programmer performing a focused bug-hunting review of a single source file. Review only the file below:

${FILE}

Your sole objective is to find genuine, reachable **bugs** in this file. Work in two phases and do not skip either.

## Scope — what counts

Only report bugs reachable through the file's **documented public API**: exported/public functions, documented behaviours and callbacks, and any code path that untrusted data can reach through a documented entry point (parsers, decoders, file-format handlers, network-input handling — a bug here counts even when it takes an attacker to trigger it).

Explicitly **ignore** any finding that is only reachable through misuse of internal interfaces:
- Bugs reachable only by calling private / non-exported / non-public-API functions, by sending crafted messages to undocumented internal processes, or by depending on implementation details that are not part of the documented public API.
- Bugs that require the caller to pass arguments violating the function's documented `@spec` / contract / type declaration. The language does not enforce these at runtime, so such misuse is uninteresting.

When in doubt about whether an entry point is public, prefer reporting only when a documented public path reaches the defect.

## Phase 1 — inventory (do not skip)

Enumerate candidate defects first, judge them second. The classes below are a **coverage floor, not a ceiling** — use them to hunt thoroughly. A real bug that fits none of them belongs in `Unclassified`; force-fitting a finding into a class that does not apply is worse than declaring it `Unclassified`.

- **Missing clause / non-total function** — a function head or `case` handling N shapes but not the (N+1)th a caller actually produces (`FunctionClauseError`, `CaseClauseError`). `with/1` is a common site: an unmatched pattern falls to `else`, and an absent `else` returns the unmatched value itself rather than raising — a silent wrong return.
- **Operator / precedence** — `and`/`&&` and `or`/`||` are not interchangeable (`and` needs a boolean; `&&` treats `nil`/`false` as falsy); `|>` binds tighter than expected; `not` vs `!`; `==` vs `===`; a guard satisfied by every input or by none.
- **Truthiness confusion** — only `nil` and `false` are falsy. A function returning `{:ok, false}` or `nil` for "absent" behaves differently under `if` than under a pattern match. Check the caller distinguishes "returned false" from "returned nothing".
- **Pattern match on the wrong shape** — matching `{:ok, x}` where the callee returns `:ok`; matching a map with more keys than the pattern assumes; matching a struct by its map shape and so accepting a different struct.
- **State / accumulator threading** — a stale binding after a rebind, an unchanged accumulator into a recursive call, the wrong tuple element returned, a field dropped across a refactor. `Enum.reduce` bodies are the usual site.
- **Off-by-one / wrong arithmetic** — `String.length` (graphemes) vs `byte_size` (bytes); `String.slice` ranges; mixing milliseconds and native time units; `div` where `rem` was intended.
- **Binary vs charlist vs string** — `String` functions on a charlist, `Enum` on a binary, `to_string/1` on something whose `String.Chars` differs from the author's assumption, or a function accepting both that behaves differently down each branch.
- **Unicode correctness** — treating a binary as characters: `String.length` counts graphemes, `byte_size` counts bytes, `String.at/2` is O(n); slicing at a byte offset can split a codepoint; case operations are locale/mode-sensitive (`String.downcase(s, :greek)`).
- **Contract violation** — a function returning a shape its `@spec`/`@doc`/doctest does not describe; a callback implementation not matching the behaviour's `@callback`; a bang function returning `{:error, _}` instead of raising, or a non-bang that raises.
- **Protocol and behaviour errors** — a `defimpl` for the wrong type; a protocol call on a type with no implementation and no fallback; an `@impl` on a non-callback; a missing optional-callback guard.
- **Macro and compile-time errors** — hygiene violations that capture or leak a variable; `unquote` at the wrong quoting depth; a macro evaluating its arguments more than once (double side effects); AST built with wrong metadata so errors point at the wrong line.
- **Process and message errors** — a `receive`/`handle_info` without a catch-all leaving messages in the mailbox forever; a monitor or timer never cleaned up; a `GenServer.call` from within the same process; a reply sent twice or not at all; linking where monitoring was meant.
- **Timeout and lifetime** — an infinite timeout where the caller expects to recover; a `Task.await` shorter than the work; a supervisor restart strategy that cannot converge.
- **Resource leak** — files, ports, ETS tables, or processes created on a path that can exit before releasing them.
- **Error-handling asymmetry** — `rescue` catching `Exception` but not `throw`/`exit`; `try/after` swallowing the original error; an error tuple silently discarded by `_ = ...` or by an unmatched `with`.
- **Dead / unreachable code** — a clause that can never match given the ones above it; an always-true guard; a branch whose condition contradicts an earlier match.
- **Documentation mismatch** — the `@doc` or a doctest describes behaviour the code does not have. A doctest that would fail if run is a bug in one of the two; say which.
- **Unclassified** — anything wrong that fits none of the above.

## Phase 2 — per finding, in order

For each candidate:
1. State the input or call sequence that triggers it.
2. Say what happens instead of what should happen — the actual error, wrong value, or hang.
3. **Reproduce it by running.** The sandbox has `elixir`, `iex`, `mix`, and `erl` built from the source under review, so a behavioural claim is settled in seconds: write the smallest script that drives it (`elixir -e '...'`), observe, and cite the output. Check `@spec`/doctest claims the same way. Fall back to a reasoned sketch only when you genuinely cannot run it — a claim you could have tested but only reasoned about is `asserted`, not `verified`.
4. Rate Critical / High / Medium / Low by what it costs a caller who hits it.

Additional obligations:
- Documentation is a contract. `@doc` and doctests are executable and published; where code and documentation disagree, say which one is wrong and why rather than assuming the code is right. A doctest that cannot currently pass is a finding.
- `@spec` disagreeing with the implementation is a finding even when no runtime failure follows, because Dialyzer consumes it and the error propagates into every caller's analysis.
- A crash is not automatically a bug: raising on invalid input is often the contract. The finding is a crash where the documented contract promises an error tuple, a crash on VALID input, or a crash whose message tells the caller nothing about what to fix.

## Output

Produce a concise markdown report and nothing else. Do not modify any files. Output only the report.

Structure the report exactly as:
- A one-sentence **Summary** section.
- A single **Bugfixes** findings section (the only findings section — do not add sections for unrelated topics).
- A closing **Risks / caveats** section.

If nothing meaningful is found in the Bugfixes section, write `No findings` there.

Each finding in the Bugfixes section begins with a level-4 heading containing only its Finding ID in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

Immediately below the heading, write these fields on separate lines, in order:

- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-parser-merge-token-quadratic`, not `CSCAN-parser-finding-1`), derived from *what the bug is* so a re-scan produces the same id. Under 40 characters; no line numbers or version numbers.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Issue** — what is wrong.
- **Class** — the Phase 1 class, or `Unclassified (<short label>)`.
- **Impact** — what it costs, in plain language, for someone who hits it (the threat/impact note for this bug).
- **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and output), `asserted` when you reasoned only. A claim you could have tested but did not is `asserted`.
- **Suggested fix** — the smallest change that removes the defect.

Findings you considered and rejected go under a `### Ruled out` heading at the end, one bullet each with the reason and its Basis (`verified`/`asserted`). Do not give those a Finding ID.

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof. A ruled-out entry whose Basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. A false positive is caught downstream; a false negative is invisible. Every claim of absence stands only when the search space and the search are named: a negative existence claim from a partial search ("this module has no X" — name where you looked), a parity claim without the upstream mechanism ("matches upstream" — name the mechanism and its default), and a mitigation the threat model does not grant ("requires authentication" — for a network-facing public API, post-auth is the attack surface) each assert absence without proof.
````
