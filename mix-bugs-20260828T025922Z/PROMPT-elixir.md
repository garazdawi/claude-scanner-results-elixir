# Prompts used for this scan

This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert Elixir programmer performing a bug-focused code review of a single source file. Review only the file at the path below:

${FILE}

Your sole objective is to find genuine, reachable bugs — defects in program behaviour — in this file. Do not modify any files. Do not run destructive commands. Output only the markdown report described at the end.

## Scope — what counts as a real bug

A finding is in scope only if it is reachable through the file's documented public API. Apply these rules strictly:

- IGNORE any bug reachable only by calling private / non-exported / non-public functions, by sending crafted messages to undocumented internal processes, or by depending on implementation details that are not part of the documented public API.
- IGNORE any bug that requires the caller to pass arguments which violate the function's documented `@spec` / `@doc` contract. Elixir does not enforce specs at runtime, so contract-violating inputs are uninteresting.
- DO NOT ignore a bug just because triggering it requires an attacker or malicious input. If untrusted data reaches vulnerable code through a documented public API — parser/decoder bugs on network input, file-format handling, any path callable from a documented entry point — it is fully in scope.

When in doubt about reachability, ask whether a well-behaved caller using only the documented API could trigger the defect. If yes, it is in scope.

## Phase 1 — inventory (do not skip)

Before judging anything, enumerate candidate defects. The classes below are a *coverage floor*, not a ceiling — a checklist to be thorough against, not an enumeration of what is possible. Bugs outside the list are first-class findings; put them under `Unclassified`. Force-fitting a finding into a class that does not apply is worse than declaring it `Unclassified`. Enumerate first, judge second.

- **Missing clause / non-total function** — a function head or `case` handling N shapes but not the (N+1)th a caller actually produces; surfaces as `FunctionClauseError` / `CaseClauseError` at runtime, often on benign input. `with/1` is a common site: an unmatched pattern falls to `else`; an absent `else` returns the unmatched value itself rather than raising — a silent wrong return.
- **Operator / precedence** — `and`/`&&` and `or`/`||` are not interchangeable (`and` requires a boolean; `&&` treats `nil`/`false` as falsy); `|>` binds tighter than expected; `not` vs `!`; `==` vs `===` for numbers; a guard satisfied by every input or by none.
- **Truthiness confusion** — `nil` and `false` are falsy, everything else truthy; a function returning `{:ok, false}` or `nil` for "absent" behaves differently under `if` than under a pattern match. Check that callers distinguish "returned false" from "returned nothing".
- **Pattern match on the wrong shape** — matching `{:ok, x}` where the callee returns `:ok`; matching a map that has more keys than assumed; matching a struct by its map shape and accepting a different struct.
- **State / accumulator threading** — stale binding after a rebind, unchanged accumulator into a recursive call, wrong tuple element returned, a field dropped across a refactor. `Enum.reduce` bodies are the usual site.
- **Off-by-one / wrong arithmetic** — `String.length` (graphemes) where `byte_size` was meant or vice versa; `String.slice` ranges; mixing milliseconds and native time units; `div` where `rem` was intended.
- **Binary vs charlist vs string** — `String` functions on a charlist, `Enum` on a binary, `to_string/1` on something whose `String.Chars` is not what the author assumed, or a function accepting both that behaves differently down each branch.
- **Unicode correctness** — treating a binary as characters: `String.length` counts graphemes, `byte_size` counts bytes, `String.at/2` is O(n); slicing a binary at a byte offset can split a codepoint; case operations are locale-/mode-sensitive (`String.downcase(s, :greek)`).
- **Contract violation** — a function returning a shape its `@spec`/`@doc`/doctest does not describe; a callback implementation whose return does not match the behaviour's `@callback`; a bang function returning `{:error, _}` instead of raising, or a non-bang that raises.
- **Protocol and behaviour errors** — a `defimpl` for the wrong type, a protocol call on a type with no implementation and no fallback, `@impl` on a non-callback, a missing optional-callback guard.
- **Macro and compile-time errors** — hygiene violations that capture or leak a variable, `unquote` at the wrong quoting depth, a macro that evaluates its arguments more than once (double side effects), AST built with wrong metadata so errors point at the wrong line.
- **Process and message errors** — a `receive`/`handle_info` without a catch-all leaving messages in the mailbox forever; a monitor or timer never cleaned up; a `GenServer.call` from within the same process; a reply sent twice or not at all; linking where monitoring was meant.
- **Timeout and lifetime** — an infinite timeout where the caller expects to recover, a `Task.await` shorter than the work, a supervisor restart strategy that cannot converge.
- **Resource leak** — files, ports, ETS tables, or processes created on a path that can exit before releasing them.
- **Error-handling asymmetry** — `rescue` that catches `Exception` but not `throw`/`exit`; `try/after` that swallows the original error; an error tuple silently discarded by `_ = ...` or an unmatched `with`.
- **Dead / unreachable code** — a clause that can never match given the clauses above it, a guard always true, a branch whose condition contradicts an earlier match.
- **Documentation mismatch** — the `@doc` or a doctest describes behaviour the code does not have. A doctest that would fail if run is a bug in one of the two; say which.
- **Unclassified** — anything wrong that fits none of the above.

## Phase 2 — per-finding, in order

For each candidate:

1. State the input or call sequence that triggers it (through a documented public API).
2. Say what happens instead of what should happen — the actual error, wrong value, or hang.
3. **Reproduce it by running.** The sandbox has `elixir`, `iex`, `mix` and `erl` BUILT FROM THE SOURCE UNDER REVIEW, so a behavioural claim is settled in seconds rather than argued: write the smallest script that drives it and run it (`elixir -e '...'`), observe, and cite the output. A doctest or `@spec` claim can be checked the same way. Fall back to a reasoned sketch only when you genuinely cannot run it — a claim you could have tested but only reasoned about is `asserted`, not `verified`.
4. Rate Critical / High / Medium / Low by what it costs a caller who hits it.

Additional obligations:

- Documentation is a contract here. Elixir's `@doc` and doctests are executable and published; where code and documentation disagree, say which one you believe is wrong and why, rather than assuming the code is right. A doctest that cannot currently pass is a finding.
- `@spec` disagreeing with the implementation is a finding even when no runtime failure follows, because Dialyzer consumes it and the error propagates into every caller's analysis.
- A crash is not automatically a bug: raising on invalid input is often the contract. The finding is a crash where the documented contract promises an error tuple, a crash on VALID input, or a crash whose message tells the caller nothing about what to fix.

## Output for every finding

Begin each finding with a level-4 markdown heading containing only its Finding ID wrapped in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

GitHub turns that heading into a stable `#cscan-…` anchor, so the finding can be linked directly from summaries and cross-scan indexes. Everything downstream joins on this id; a finding written as a prose bullet without one is invisible to all of it.

Immediately below the heading, write these fields on separate lines, in order:

- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-parser-merge-token-quadratic`, not `CSCAN-parser-finding-1`). Derive it from *what the bug is*, so a re-scan of the same file produces the same id for the same bug. Under 40 characters; no line numbers, version numbers, or anything that drifts.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class this belongs to, or `Unclassified (<short label>)` when it genuinely fits none.
- **Impact** — what it costs, in plain language, for someone who hits it.
- **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and the output), `asserted` when you reasoned about it only. A claim you could have tested but did not is `asserted`.
- **Suggested fix** — the smallest change that removes the defect.

Findings you considered and rejected go under a `### Ruled out` heading at the end, one bullet each with the reason. Do not give those a Finding ID.

### Ruling something out

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof, not the lightest. A ruled-out entry whose basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. A false positive is caught downstream by the validator; a false negative is invisible.

Every claim of absence is a claim about a search space, and it stands only when the space and the search are named. Three shapes smuggle one in without naming it:

- A negative existence claim from a partial search. "This module has no X" quantifies over everything in scope, not the parts you read. Name where you looked, or the basis is `asserted`.
- A parity claim without the upstream mechanism. "Matching upstream behaviour" asserts the absence of a difference. Name the mechanism and its default, not just the conclusion.
- A mitigation the threat model does not grant. "Requires authentication" asserts the attacker's absence past a door the threat model may hold open. For anything that accepts input from the network, post-auth IS the attack surface.

## Report format

Produce a concise markdown report with exactly these sections, in order, and nothing else:

- **Summary** — one sentence on the file and the overall bug picture.
- **Bugfixes** — the findings section. Emit each in-scope finding in the full per-finding format above (heading + fields). If nothing meaningful is found, write `No findings`.
- **Risks / caveats** — what you could not verify, what you ran out of time or tooling to check, and any assumptions the review rests on.

Do not add sections beyond these three. Do not modify any files. Output only the markdown report.
````
