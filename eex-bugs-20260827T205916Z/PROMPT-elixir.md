# Prompts used for this scan

This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert Elixir programmer performing a bug-focused code review of a single source file. Review only this file:
${FILE}

Your sole objective is to find real bugs — defects that produce a crash, a wrong value, a hang, a leak, or a documentation/spec contract violation — that are reachable through the file's documented public API.

Scope — what counts and what does not:
- Focus exclusively on issues reachable through documented public APIs. Treat data arriving through a documented public entry point as potentially untrusted: parser/decoder bugs on network input, file-format handling, and any code path callable from a documented entry point are all in scope even when exploitation requires a hostile caller or crafted input.
- Ignore any finding that is only reachable through misuse of internal interfaces. Specifically exclude: bugs reachable only by calling private / non-exported / non-public-API functions, by sending crafted messages to undocumented internal processes, or by depending on implementation details that are not part of the documented public API.
- Exclude bugs that require the caller to pass arguments which violate the function's documented `@spec` / contract / header declaration. Elixir does not enforce these at runtime, so such "bugs" are uninteresting.

Phase 1 — inventory (do not skip)

The classes below are a coverage floor, not a ceiling. They list the failure shapes worth hunting in Elixir code; use them to be thorough, not as an enumeration of possibility. Bug findings outside the list are first-class — the `Unclassified` class at the end is where they go, and force-fitting a finding into a class that doesn't apply is worse than declaring it `Unclassified`. Enumerate first, judge second.

- Missing clause / non-total function — a function head or `case` that handles N input shapes but not the (N+1)th a caller actually produces. In Elixir this surfaces as `FunctionClauseError` or `CaseClauseError` at runtime, often on a benign input. `with/1` is the common site: an unmatched pattern falls to `else`, and an absent `else` returns the unmatched value itself rather than raising — a silent wrong return.
- Operator / precedence — `and`/`&&` and `or`/`||` are not interchangeable (`and` requires a boolean, `&&` treats `nil`/`false` as falsy); `|>` binds tighter than most people expect; `not` vs `!`; `==` vs `===` for numbers; a guard that is satisfied by every input or by none.
- Truthiness confusion — `nil` and `false` are falsy and everything else is truthy, so a function returning `{:ok, false}` or `nil` for "absent" behaves differently under `if` than under a pattern match. Check that the caller distinguishes "returned false" from "returned nothing".
- Pattern match on the wrong shape — matching `{:ok, x}` where the callee returns `:ok`, matching a map that has more keys than the pattern assumes, matching a struct by its map shape and so accepting a different struct.
- State / accumulator threading — using a stale binding after a rebind, passing an unchanged accumulator into a recursive call, returning the wrong element of a tuple, dropping a field across a refactor. `Enum.reduce` bodies are the usual site.
- Off-by-one / wrong arithmetic — `String.length` (graphemes) where `byte_size` was meant or vice versa; `String.slice` ranges; mixing milliseconds and native time units; `div` where `rem` was intended.
- Binary vs charlist vs string — `String` functions on a charlist, `Enum` on a binary, `to_string/1` on something whose `String.Chars` is not what the author assumed, or a function that accepts both and behaves differently down each branch.
- Unicode correctness — treating a binary as a sequence of characters: `String.length` counts graphemes, `byte_size` counts bytes, and `String.at/2` is O(n). Slicing a binary at a byte offset can split a codepoint. Case operations are locale- and mode-sensitive (`String.downcase(s, :greek)`).
- Contract violation — a function that returns a shape its `@spec`, `@doc`, or doctest does not describe; a callback implementation whose return does not match the behaviour's `@callback`; a bang function that returns `{:error, _}` instead of raising, or a non-bang that raises.
- Protocol and behaviour errors — a `defimpl` for the wrong type, a protocol call on a type with no implementation and no fallback, an `@impl` annotation on a function that is not a callback, a missing optional-callback guard.
- Macro and compile-time errors — hygiene violations that capture or leak a variable, `unquote` in the wrong quoting depth, a macro that evaluates its arguments more than once (double side effects), AST built with the wrong metadata so errors point at the wrong line.
- Process and message errors — a `receive` or `handle_info` without a catch-all that leaves messages in the mailbox forever; a monitor or timer never cleaned up; a `GenServer.call` from within the same process; a reply sent twice or not at all; linking where monitoring was meant.
- Timeout and lifetime — an infinite timeout where the caller expects to recover, a `Task.await` shorter than the work, a supervisor restart strategy that cannot converge.
- Resource leak — files, ports, ETS tables, or processes created on a path that can exit before releasing them.
- Error-handling asymmetry — `rescue` that catches `Exception` but not `throw`/`exit`, `try/after` that swallows the original error, an error tuple silently discarded by `_ = ...` or by an unmatched `with`.
- Dead / unreachable code — a clause that can never match given the clauses above it, a guard that is always true, a branch whose condition contradicts an earlier match.
- Documentation mismatch — the `@doc` or a doctest describes behaviour the code does not have. A doctest that would fail if run is a bug in one of the two, and worth saying which.
- Unclassified — anything wrong that doesn't fit above.

Phase 2 — per-finding, in order

For each candidate: (1) state the input or call sequence that triggers it. (2) Say what happens instead of what should happen — the actual error, wrong value, or hang. (3) Reproduce it by running. The sandbox has `elixir`, `iex`, `mix` and `erl` BUILT FROM THE SOURCE UNDER REVIEW, so a behavioural claim is settled in seconds rather than argued: write the smallest script that drives it and run it (`elixir -e '...'`), observe, and cite the output. A doctest or `@spec` claim can be checked the same way. Fall back to a reasoned sketch only when you genuinely cannot run it — a claim you could have tested but only reasoned about is `asserted`, not `verified`. (4) Rate Critical / High / Medium / Low by what it costs a caller who hits it.

Phase 2 — additional obligations

- Documentation is a contract here. Elixir's `@doc` and doctests are executable and published; where code and documentation disagree, say which one you believe is wrong and why, rather than assuming the code is right. A doctest that cannot currently pass is a finding.
- `@spec` disagreeing with the implementation is a finding even when no runtime failure follows, because Dialyzer consumes it and the error propagates into every caller's analysis.
- A crash is not automatically a bug: raising on invalid input is often the contract. The finding is a crash where the documented contract promises an error tuple, a crash on VALID input, or a crash whose message tells the caller nothing about what to fix.

Output — the report

Do not modify any files. Output only the markdown report, nothing else. Keep it concise.

Structure the report exactly as:
1. A `## Summary` section: one sentence.
2. A `## Bugfixes` section: the bulleted findings (see per-finding format below). Write `No findings` if nothing meaningful is found.
3. A `## Risks / caveats` section.

Include only these sections — no unrelated sections.

Output for every finding

Begin each finding with a level-4 markdown heading containing only its Finding ID wrapped in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

GitHub turns that heading into a stable `#cscan-…` anchor, so the finding can be linked directly from summaries and cross-scan indexes. Everything downstream — deduplication, validation, the fix sweep, the triage issue a maintainer actually reads — joins on this id. A finding written as a prose bullet without one is invisible to all of it, however good the analysis is.

Immediately below the heading, write these fields on separate lines, in order:

- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-compiler-merge-token-quadratic`, not `CSCAN-compiler-finding-1`). Derive it from what the bug is, so a re-scan of the same file produces the same id for the same bug and downstream tracking stays stable. Under 40 characters; no line numbers, version numbers, or anything that drifts.
- **Severity** — Critical / High / Medium / Low. Triage filters on this.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class this belongs to, or `Unclassified (<short label>)` when it genuinely fits none.
- **Issue** — what is wrong.
- **Impact** — what it costs, in plain language, for someone who hits it, and the threat note: how untrusted input reaches it through a documented public API.
- **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and the output), `asserted` when you reasoned about it only. A claim you could have tested but did not is `asserted`.
- **Suggested fix** — the smallest change that removes the defect.

Findings you considered and rejected go under a `### Ruled out` heading at the end of the Bugfixes section, one bullet each with the reason. Do not give those a Finding ID.

Ruling something out

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof, not the lightest. A ruled-out entry whose Basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. A false positive is caught downstream by the validator; a false negative is invisible, which is why the asymmetry runs this way.

Every claim of absence is a claim about a search space, and it stands only when the space and the search are named. Three shapes smuggle one in without naming it:

- A negative existence claim from a partial search. "This module has no X" quantifies over everything in scope, not over the files you opened. Name where you looked, or the Basis is `asserted`.
- A parity claim without the upstream mechanism. "Matching upstream behaviour" asserts the absence of a difference. Name the mechanism and its default rather than asserting sameness.
- A mitigation the threat model does not grant. "Requires authentication" asserts the attacker's absence past a door the threat model may hold open. For a server that accepts credentials from the network, post-auth IS the attack surface.
````
