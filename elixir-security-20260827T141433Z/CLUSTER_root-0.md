# Cluster cross-file findings

#### `CSCAN-cluster-compiler-module-pool-atom-leak`

- **Finding ID** — `CSCAN-cluster-compiler-module-pool-atom-leak`
- **Severity** — Medium
- **Confidence** — high
- **Files involved**
  - `elixir_compiler.erl:82` (`retrieve_compiler_module()` inside `spawned_compile/3`), `:86` (`noenv_forms`, the raise site), `:100-105` (`dispatch/4`, the `try/after` that returns the module), `:126-130` (retrieve/return wrappers)
  - `elixir_code_server.erl:65-71` (`retrieve_compiler_module` handler — mints atom + `Counter+1` when `Unused == []`), `:102-105` (`return_compiler_module` — the only path that puts a module back), `:160-161` (`compiler_module/1` → `list_to_atom("elixir_compiler_" ++ integer_to_list(I))`)
  - Supporting (out of cluster, read for confirmation): `elixir_erl_compiler.erl:9-40` (`spawn/1` re-raises child crash at `:37-39`), `:87-118` (`noenv_forms` error paths); `elixir_errors.erl:309-313` (`compile_error/3` is `-> no_return()`)
- **Finding shape** — "Safe because the caller checks" broken (a cross-file resource-lifecycle invariant — "every retrieved compiler module is returned" — that `elixir_code_server` relies on to bound atom creation, but that `elixir_compiler` violates on its crash path). Maps to the threat model's in-scope **atom-table exhaustion** / **unbounded resource growth** DoS.
- **Evidence**
  - `elixir_code_server.erl` bounds atom growth *only* if every retrieved module is returned: `handle_call(retrieve_compiler_module, …)` pulls from `Unused` when non-empty (`:66-68`, counter unchanged), but when `Unused == []` it calls `compiler_module(Counter)` and advances the counter (`:69-70`); `compiler_module/1` mints a brand-new permanent atom `elixir_compiler_<N>` (`:160-161`). The **only** way a module re-enters the pool is `return_compiler_module` (`handle_cast`, `:102-105`).
  - In `elixir_compiler.erl`, the retrieval happens *inside the spawned child* (`spawned_compile/3`, `:82`) and the matching return happens *only* in `dispatch/4`'s `after` (`:104`). But `dispatch/4` is called (`compile/4:76`) **only after** `elixir_erl_compiler:spawn(...)` returns successfully. If `code_mod` (`:84`), `noenv_forms` (`:86`), `code:load_binary` (`:87`) or `is_purgeable` (`:88`) raises, the child crashes, `spawn/1` re-raises (`elixir_erl_compiler.erl:37-39`), the `{Module, Fun, LabelledLocals} = …` match at `elixir_compiler.erl:72-73` never binds, and `dispatch/4` — hence `return_compiler_module` — is never reached. The retrieved module (held only in the dead child's `Module` var) is leaked.
  - The raise on `:86` is real and reachable from generated forms: `noenv_forms` routes Erlang back-end errors through `format_errors`/`incompatible_options` → `elixir_errors:compile_error/3` (`-> no_return()`, `elixir_errors.erl:309-313`), and `elixir_erl_compiler.erl:172-176` has dedicated handling for `beam_validator` errors on the compiled forms — i.e. the Elixir team explicitly anticipates the Erlang compiler rejecting successfully-*expanded* code on exactly this path.
  - Net effect: each leaked slot permanently shrinks `Unused`, so sustained post-retrieve crashes drive `Unused` empty and make every subsequent retrieval mint a new atom and bump `Counter` without bound → the process-global atom table grows monotonically until the BEAM aborts (`system_limit`, default ~1,048,576 atoms). The reachable entry point is `elixir_compiler:quoted/3 → optimize_defmodule/2 → compile(Forms,[],[],E)` (`:43`) for any non-`defmodule` top-level form, i.e. `Code.compile_string`/`Code.eval_string` of an attacker-supplied expression.
- **What the per-file pass missed** — The `elixir_code_server` reviewer could see the atom is minted on a monotonic counter but could not see whether the counter is bounded, because that depends on `elixir_compiler`'s crash-path return behavior (it wrote `Depends on: elixir_compiler.erl` and left it asserted); the `elixir_compiler` reviewer examined `compile/4` only for code-execution and recorded "Not examined: none," never linking a `spawned_compile` crash to unbounded atom creation in `elixir_code_server` — the leak only exists in the seam between the two files.
- **Suggested fix** — Make retrieval/return crash-safe as a pair. Minimal option: move `retrieve_compiler_module()` out of `spawned_compile/3` and into `dispatch/4`'s `try` (or wrap the retrieve→compile span in its own `try … after return_compiler_module(Module, …) end`) so any failure between retrieve and load still returns the slot. Alternatively, in `elixir_code_server`, have the `retrieve` handler monitor the borrowing pid and reclaim the module to `Unused` on its `'DOWN'` (the server already monitors compiling pids for `defmodule`), so a crashed borrower can never permanently consume a pool slot / atom.
