# Cluster cross-file findings

#### `CSCAN-cluster-info-source-path-terminal-escape`

- **Finding ID** — `CSCAN-cluster-info-source-path-terminal-escape`
- **Severity** — Low
- **Confidence** — high
- **Files involved**
  - `elixir/lib/iex/lib/iex/info.ex:100` (`info_module/1`), `:110` (`{"Module bytecode", module_object_file(mod)}`), `:111` (`{"Source", module_source_file(mod_info)}`), `:149-154` (`module_object_file/1` → `Path.relative_to_cwd`), `:160-162` (`module_source_file/1` → `Path.relative_to_cwd`)
  - `elixir/lib/iex/lib/iex/helpers.ex:573-584` (`i/1`), specifically `:575` (`++ IEx.Info.info(term) ++`), `:578` (the only string massaging), `:580` (`IO.puts(IEx.color(:eval_info, "  #{info}"))`)
  - (supporting, out of cluster) `elixir/lib/iex/lib/iex.ex:627-641` (`IEx.color/2` does not scrub escapes); `introspection.ex` independently verified `Path.relative_to_cwd/1` preserves ESC/BEL
- **Finding shape** — Taint across files / output-neutralization (terminal-escape injection, CWE-150), plus a "safe because the consumer escapes" assumption broken across the two files.
- **Evidence**
  - `info.ex` emits two **raw, un-inspected** strings for a module term. `module_source_file/1` (`:160-162`) returns `Path.relative_to_cwd(mod_info[:compile][:source])` and `module_object_file/1` (`:149-154`) returns `Path.relative_to_cwd(path)`. Every *other* externally-derived field in this file is wrapped in `inspect/1` (e.g. `:113` `module_compile_options` → `inspect`, `:118` `Raw representation` → `inspect`), but these two paths are not — `Path.relative_to_cwd/1` returns the bytes verbatim.
  - `mod_info[:compile][:source]` is the compile-time source path baked into the module's `.beam`. It is attacker-influenceable: it is the *same* value the `introspection.ex` HIGH finding (`CSCAN-introspection-editor-os-cmd-injection`) treats as attacker-controlled, and `introspection.ex` empirically verified `Path.relative_to_cwd("lib/foo\e[31mHACK\e[0m\a.ex")` preserves ESC and BEL.
  - `helpers.ex` `i/1` consumes the protocol output at `:575` and, for each `{subject, info}`, does only `info |> to_string() |> String.trim() |> String.replace("\n", "\n  ")` (`:578`) — none of which strips C0/ESC — then prints it with `IO.puts(IEx.color(:eval_info, "  #{info}"))` (`:580`). `IEx.color/2` (iex.ex:630) states "ANSI escapes in `string` are not processed in any way." So the raw path bytes reach the terminal unscrubbed.
  - Result: a developer running `i(HostileModule)` on a module whose compiled-in `:source` path (or loaded `.beam` path) contains ANSI/C0 escapes — a malicious dependency shipping a source file named `evil\e[2J.ex`, or a forged `.beam` with a crafted `:source` attribute — has those escapes rendered to their terminal (cursor manipulation, screen clobbering, misleading output, title/clipboard abuse on permissive emulators).
- **What the per-file pass missed** — `info.ex`'s reviewer concluded "every externally derived value reaches output through `inspect`, which escapes" and classified the source/bytecode paths as display-only trusted metadata, never inspecting the *consumer*; `helpers.ex`'s reviewer reviewed many helpers but never analyzed `i/1`'s raw printing of `IEx.Info.info` values at all — so only by reading the producer (`info.ex`) and the raw-`IO.puts` consumer (`helpers.ex`) together does the un-escaped path→terminal chain appear. It is a distinct file pair from the existing `CSCAN-crossfile-source-derived-terminal-escape-passthrough` finding (which covers only `server.ex`/`pry.ex`/`introspection.ex`); the IO-layer scrubber that finding proposes for those three files would not cover the `i/1` path.
- **Suggested fix** — Minimal: in `info.ex`, wrap the two path fields in `inspect/1` as the sibling fields already are — `module_source_file/1` → `default_or_apply(source, &inspect(Path.relative_to_cwd(&1)))` and likewise `module_object_file/1`. Alternatively (and covering the other three sinks too), route `helpers.ex` `i/1`'s per-line output at `:580` through a shared control-character scrubber (strip C0 except `\t`/`\n`, and CSI/OSC sequences) before `IO.puts` — the same IO-layer mitigation the existing cross-file finding recommends.
