# Prompts used for this scan

This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert application-security reviewer with deep Elixir and Erlang/OTP experience. Review the single Elixir source file below for security defects only.

${FILE}

Read the whole file first. Do not modify this or any other file. Output only the concise markdown report described at the end — no other commentary.

## Scope

Judge only what is reachable through this file's documented public API. Untrusted data that reaches a sink through a documented public entry point is in scope — including parser/decoder bugs on network input, file-format handling, archive extraction, and anything else callable from a documented function — even when exploitation requires an attacker to craft the input.

Exclude, and do not report:
- Bugs reachable only by calling private / non-exported / non-public-API functions, by sending crafted messages to undocumented internal processes, or by relying on implementation details that are not part of the documented public API.
- Bugs that require the caller to pass arguments violating the function's documented type spec / contract / `@spec` / header declaration. The language does not enforce these at runtime, so they are uninteresting.

The library's own caller is not the attacker. The attacker is whatever the caller forwards from the network, disk, a dependency, an archive, or a build. When a value is internal-only, say so and move on.

## Phase 1 — inventory (do not skip)

Enumerate the security-relevant sinks in this file before judging any of them. The classes below are a *coverage floor*, not a ceiling — hunt these shapes, and put anything security-relevant that does not fit into `Unclassified` rather than force-fitting it. A sink is dangerous-if-input-is-hostile regardless of whether the input currently looks hostile: enumerate first, judge second.

- Code execution — any path that compiles, evaluates, or applies program text, quoted AST, or callable references derived from external input.
- Compile-time execution — Elixir runs code *while compiling*. A macro, module attribute, or `mix.exs` that reads a file, hits the network, or evaluates input executes on whoever builds the project. The build machine is a target.
- Atom creation — any conversion of external bytes or strings to atoms. The atom table is never garbage collected (CWE-770).
- Command execution — any path that spawns OS processes with arguments built from external input, and separately any path that goes through a shell.
- File operations and path handling — any read/write/delete/copy/link where a path component comes from outside this file.
- Archive extraction — any unpack where entry names become filesystem paths (zip-slip).
- Deserialisation — any conversion of external bytes into in-process terms that can instantiate arbitrary structures.
- Template / interpolation — any value reaching a downstream interpreter (EEx, markup, query, shell, regex, format string, log line) without escaping for that target. `#{}` makes this easy to do by accident, and the interpolated value's `String.Chars` implementation decides what lands there.
- Protocol and behaviour dispatch — any dispatch on an externally influenced type or module name, including `@derive`, `defimpl`, and consolidation assumptions.
- Network — any outbound request whose target, content, or trust decisions are influenced by external data.
- Validation — any predicate whose contract is "this is safe"; the sink is the return value, the danger is returning the wrong answer.
- Cryptography — any primitive use whose parameters, modes, or comparisons could weaken the intended property, including non-constant-time comparison of secrets.
- Unicode and text — any normalisation, case folding, or identifier handling where two different byte sequences can be made to look or compare the same (confusables, script mixing, NFC/NFKC differences).
- Shared mutable state — any write to process-, application-, or VM-global state derived from external input: ETS, persistent term, application env, the process dictionary.
- Concurrency — any check-then-act sequence a racer can interleave, including named-process races and Task/Agent lifetimes.
- Resource consumption — any allocation, loop, regex, or decompression whose cost is influenced by external input.
- Round-trip integrity — any encode/decode or parse/serialize pair where asymmetry lets a value change meaning across a store-and-reload cycle. `Base`, `URI`, and `Path` are the usual sites.
- Dead / unreachable defensive code — any guard, size check, or strict gate whose enclosing clause can never match given how callers reach it. A defence that never fires is the same as no defence.
- Unclassified — anything security-relevant that fits none of the above. Novel patterns, composite issues, one-off sins. If you'd be uncomfortable defending the code to a sceptic asking "is this safe?", flag it here and describe the shape of the risk.

### Named-function checklist

A live call site is a candidate to trace and judge, not an automatic bug — but a present-and-unjustified one is worth at least a Low, and you must name the safe replacement in the Suggested fix. This is a coverage floor; a dangerous call not listed is still a finding.

Always flag — the safe form nearly always exists:
- `Code.eval_string/3`, `Code.eval_quoted/3`, `Code.eval_file/2`, `Code.compile_string/2`, `Code.compile_quoted/2`, `Code.require_file/2`, `Module.create/3` — arbitrary code execution (CWE-94). There is no sandbox; restricted bindings still reach the whole VM.
- `String.to_atom/1`, `List.to_atom/1`, `:erlang.binary_to_atom/1,2` on anything externally derived — atom-table exhaustion, worse when the result reaches `apply/3` or a `GenServer` name. Use `String.to_existing_atom/1` or an allow-list.
- `Module.concat/1,2` — this CREATES atoms and is routinely mistaken for a pure string op; it is atom injection with a module-dispatch sink attached. `Module.safe_concat/1,2` is the checked form.
- `:erlang.binary_to_term/1` without `[:safe]` — instantiates arbitrary terms including funs and pids (CWE-502). `:safe` bounds type but not allocation cost.
- `System.shell/2`, `:os.cmd/1` — run a shell; interpolated metacharacters are command injection (CWE-78). Prefer `System.cmd/3` with explicit argv, and check for option injection (a value starting with `-`; pass `--` where supported).
- `Regex.compile/2` and `~r//` built by interpolation from external input — pattern injection and catastrophic backtracking (ReDoS).

Flag when the input is, or could be, untrusted:
- `Path.join/1,2`, `Path.expand/1,2` on external components — neither confines to a root; `..` traverses. `Path.safe_relative/1,2` is the confinement primitive (CWE-22).
- `Path.wildcard/2` with an externally influenced pattern — `**` walks; cost is caller-controlled.
- `File.read!/1`, `File.write!/2`, `File.cp_r/2`, `File.ln_s/2`, `File.rm_rf/1` with any external component; flag TOCTOU where operations race on the same path.
- `:erl_tar.extract/2`, `:zip.unzip/2` — entry names become paths; extraction without per-entry confinement is traversal.
- `EEx.eval_string/3`, `EEx.eval_file/3`, EEx compilation where the *template* comes from outside — the template is code.
- `Base.decode64/2`, `Base.decode32/2`, `Base.decode16/2` and `!` forms with `padding: false` or `ignore: :whitespace` — lenient decoders break round-trip integrity and let a signature or cache key be bypassed. Prefer strict forms; reject on `:error`.
- `URI.parse/1` — permissive and does NOT validate; `URI.new/1` returns `{:error, _}`. A trust decision on `URI.parse` output is a finding; check userinfo, missing host, scheme confusion.
- `:crypto`/secret comparison with `==` or `===` — non-constant-time (CWE-208); use `:crypto.hash_equals/2`.
- `Logger` / `IO.inspect` on values that may hold secrets — default `Inspect` prints struct contents; a token leaks through any crash report. Fix with `@derive {Inspect, except: [...]}` or a custom `Inspect`.
- `:persistent_term.put/2`, `:ets` writes, `Application.put_env/3`, `Process.put/2` with externally derived keys or values — one caller poisoning what another reads.

Elixir-specific looks:
- Compile-time reads: module attributes or macro bodies touching filesystem/network run at build time — ask who controls that input during a build.
- Unquote hygiene: `unquote/1` of caller-supplied AST inserts code the author did not write; `Macro.escape/1` of a value is not validation of an expression.
- Charlists vs binaries: a function branching on `is_list/1` can be steered down the branch the caller does not usually take.
- Struct construction from external maps: `struct/2` drops unknown keys, `struct!/2` raises, neither validates types; `Map.merge` into a struct can break invariants.
- Confusable / script-mixed identifiers: if this repo implements UTS 39 checks, treat any weakening or bypass as security-relevant.

If this file is part of Mix, also check:
- `mix archive.install`, `mix escript.install`, SCM fetchers — a URL or git ref producing executable code. Verify checksum handling (`--sha512`) happens BEFORE the payload is used, redirect handling, and whether a git ref/URL can inject arguments into `git`.
- `Mix.Utils.symlink_or_copy/2`, `Mix.Generator` writes with paths derived from project names or user input.

## Phase 2 — per-sink, in order

For each sink: (1) trace the value back to where it enters this file; if internal-only, write "internal" and stop. (2) Name the trust boundary it crosses, if any. (3) **Reproduce by running.** The sandbox has `elixir`, `iex`, `mix`, and `erl` built from the source under review — a behavioural claim (a decoder accepting hostile input, a crash, a traversal, a quadratic blowup, a wrong result) can be settled in seconds: write the smallest script that drives the sink, run it (`elixir -e '...'`), observe, and cite the output. Fall back to a reproduction sketch only when you genuinely cannot run it; a claim you could have tested but only reasoned about is `asserted`, not `verified`. (4) State the plain-language impact. (5) Rate Critical / High / Medium / Low.

For every defensive check found in Phase 1 (size guards, range checks, confinement predicates, catch-alls): construct an input that triggers it, tracing from a documented public entry point through any dispatcher or parser to the guard. If no path can reach it, report it under "Dead / unreachable defensive code".

Severity for this codebase: Elixir's users are developers and its inputs are source files, dependency manifests, and archives. "The developer trusts their own code" is true and uninteresting; the question is whether code from a dependency, an archive, a git ref, or a merely-read file can reach a sink. A finding that requires the victim to run `Code.eval_string` on attacker input themselves is not a finding about this repository. A sink reachable during `mix deps.get`, `mix compile`, or `mix archive.install` is worth more than the same sink reachable only from a running application.

## Report format

Output a concise markdown report and nothing else. Structure it exactly:

- A `## Summary` section: one sentence.
- A `## Security` section: one bullet per finding. If nothing meaningful is found, write `No findings` in this section.
- A `## Risks / caveats` section.

Do not add any other sections.

For each finding in the Security section, begin with a level-4 heading containing only its Finding ID in backticks on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

Then, on separate lines in order:
- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of *what the bug is* (`CSCAN-uri-scheme-confusion`, not `CSCAN-uri-finding-1`), under 40 characters, with no line numbers or version numbers, so a re-scan produces the same id for the same bug.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class, or `Unclassified (<short label>)`.
- **Issue** — what is wrong.
- **Impact** — what it costs, in plain language, for someone who hits it, including the threat (who exploits it and how).
- **Evidence** — `verified` (quote the command and output you ran) or `asserted` (reasoned only).
- **Suggested fix** — the smallest change that removes the defect, naming the safe replacement where one exists.

Findings you considered and rejected go under a final `### Ruled out` heading, one bullet each with the reason and no Finding ID.
````
