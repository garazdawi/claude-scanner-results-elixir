## Summary
`Mix.Tasks.Profile.Fprof` is a developer-facing profiler whose entire attack surface is operator-supplied CLI argv (the code/script to profile and profiling options) plus machine-generated `:fprof` analysis output, so no dependency/archive/network/read-file data reaches a sink and there are no findings.

## Security

No findings.

### Ruled out

- **`Code.string_to_quoted!/1` + `Code.compile_quoted/1` in `profile_code/2` (lines 168, 175) — code execution.** The `code_string` is the developer's `-e`/`--eval` expression or the contents of a script file the developer named on the command line (fed via `Mix.Tasks.Run.run/5`'s `expr_evaluator`/`file_evaluator` callbacks). This is by design and identical to `mix run` — the operator is compiling/executing their own code. No dependency, archive, git ref, or project-read file influences this text. Out of scope per the threat model (the operator is not the attacker).
- **`File.read!(&1)` in `run/1` (line 157) — path/file read.** The path is the developer-supplied positional argument, validated by `File.regular?` in `Run.run/5` before use. Operator-controlled path; no external component.
- **`next_term/1` → `:erl_scan.tokens` + `:erl_parse.parse_term` (lines 259–263) — atom creation / deserialisation.** The parsed text is `:fprof.analyse` output, generated by Erlang's fprof from profiling the developer's own code. Every atom produced (`:undefined`, `:suspend`, `:totals`, `:spawned_by`, module/function names, pid-representation atoms) already exists in the atom table or is bounded by the developer's chosen code; it is not attacker-controlled and cannot exhaust the atom table from a remote source. `parse_term` builds only ground terms (no live pids/funs). Verified: ran `profile/2` end-to-end with `callers:`/`details:` and observed correct round-trip and return value `1001000`.
- **`:io.format(format, data)` in `print_row/2` (line 336) — format-string / template injection.** The format string is assembled solely from the constant `@columns` and caller-literal format lists (`["s","B",".3f",".3f","s"]`); all fprof-derived values are passed as `~s`/`~B`/`~.3f` **data** arguments, so a `~` inside a function name cannot become a directive. No injection.
- **`Path.join`/`Path.expand` on the trace file (lines 214–218) and `File.rm` (line 245) — path handling / TOCTOU.** Filename is `fprof_trace_<System.os_time()>` in `System.tmp_dir!()`; both components are trusted (an integer timestamp and the system temp dir). See caveat on predictability below.
- **`parse_opt/1` (lines 178–181) — atom creation from options.** Only the fixed literals `"acc"`/`"own"` map to atoms; any other value is passed as data into `Mix.raise` (not `String.to_atom`). No dynamic atom injection.
- **Hard-match assertions** `{:ok, term} = :erl_parse.parse_term(...)`, `{:ok, tracer} = :fprof.profile([:start])`, `{:ok, analyse_dest} = StringIO.open("")` — could raise `MatchError`, but only on self-generated/local-runtime failures, not across a trust boundary; a crash here is at most a self-inflicted abort of the developer's own profiling run.

## Risks / caveats
- **Predictable trace-temp-file name (CWE-377), not reported.** With `--trace-to-file`, the file is `System.tmp_dir!()/fprof_trace_<System.os_time()>`, a non-exclusive, guessable-scheme name in a shared temp dir; fprof opens it for writing without `O_EXCL`, so in principle a local co-resident user who pre-creates a symlink could redirect the trace write. I judged this below reporting threshold because (a) the threat model scopes the attacker as *remote* content (dependencies/archives/network/read files), not a local OS/BEAM neighbor; (b) `System.os_time()` is nanosecond-resolution (verified: `1787829573839155651`), making the exact name effectively unguessable within the sub-millisecond open window; and (c) it is behind an explicit opt-in flag. Worth a hardening note (`File.open` with `[:exclusive]` or a random suffix) but not a vulnerability under this trust model.
- I exercised the documented `profile/2` public function and the `--trace-to-file`/`callers`/`details`/`sort` option paths directly and confirmed cleanup of the trace file. I did not fuzz `:fprof.analyse` output shapes into `next_term/1`; malformed analysis output would cause a self-inflicted `MatchError` crash of the developer's own run, which is not a cross-boundary security issue.
