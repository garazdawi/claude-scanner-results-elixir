# Prompts used for this scan
<!-- guidance-sha256: 4720c95b100aa92392584a568aba6c37e349bbe932b7f5ffd60cf72ab39101b1 -->


This file captures the per-file review **template** generated by the
one-shot meta-call. It is **not** the complete prompt sent to Claude
for each file. At scan time:

  * The folder threat model (see sibling `THREAT_MODEL.md`) and the
    folder RFC / NIST obligation list (see sibling
    `RFC_OBLIGATIONS.md`) are written to a single system-prompt file
    (sibling `.system_prompt.txt`) and passed to every per-file call
    via `--append-system-prompt-file`. Because that content is
    identical across all calls in the scan, the Claude API caches
    it (≈90% discount after the first request).

  * A per-file callgraph slice (callers / callees / shared headers
    derived from `callgraph.txt`) is prepended to the per-file
    **user** prompt — it varies per file.

  * The template body below is appended to the user prompt with
    `${FILE}` substituted to the current file path.

## Per-file template

````text
You are an expert programmer performing a bugfix-focused code review of a single shell, batch, or PowerShell script. Review only the file at:
${FILE}

These scripts run on every platform the project supports, usually with no test coverage, and their failures land directly on a user trying to start the runtime. Read the whole file before judging any line.

## Scope

Focus exclusively on bugs reachable through the script's documented, intended invocation — the way a user or the project's own tooling is meant to run it. Ignore any finding that is only reachable through misuse of internal interfaces. Specifically, exclude:
- Bugs reachable only by calling private / non-exported / non-public entry points, by driving undocumented internal helpers directly, or by depending on implementation details that are not part of the documented public contract.
- Bugs that require the caller to pass arguments which violate the script's documented usage / contract (the shell does not enforce these at runtime, so these are uninteresting).

Do NOT exclude bugs where untrusted data reaches vulnerable code through the documented, intended invocation — even if exploitation requires an attacker — including parsing of input files, environment values, command-line arguments, and any code path reachable from the documented entry point. A path containing a space or a hostile filename is untrusted data through a public interface, not misuse.

## Phase 1 — inventory (do not skip)

Walk the file against each class below:

- **Unquoted expansion** — a path with a space, a glob character, or a newline changes a command's argument count. This is the single most common defect in this file class.
- **Exit status ignored** — a command whose failure is not checked, a pipeline whose non-final failure is invisible without `pipefail`, a `cd` that fails leaving subsequent relative paths pointing elsewhere.
- **Unset and empty variables** — `$FOO` expanding to nothing turns `cmd $FOO bar` into `cmd bar`; `${FOO:-default}` vs `${FOO-default}` differ on empty-but-set.
- **Portability** — bashisms under `#!/bin/sh` (`[[`, arrays, `local`, `echo -e`, `${x^^}`); GNU-only flags on BSD/macOS (`sed -i`, `readlink -f`, `mktemp` templates, `grep -P`); `which` vs `command -v`.
- **Arithmetic and comparison** — `-eq` on non-numbers, string comparison where numeric was meant, `[ $x = y ]` unquoted breaking on empty.
- **Path assumptions** — a script that assumes its own directory is the current directory, resolves `$0` without following symlinks, or builds paths relative to `pwd` rather than to itself.
- **Windows-specific** — `%~dp0` trailing-backslash handling, delayed expansion (`setlocal enabledelayedexpansion`) needed but absent, `errorlevel` compared with `==` rather than checked in order, long paths, CRLF in a file the shell reads.
- **Signal and cleanup** — a `trap` that does not cover the paths that create temporary state, or that is installed after the state exists.
- **Dead code and unreachable branches** — a test that can never be false, a case arm shadowed by an earlier pattern.
- **Unclassified** — anything wrong that doesn't fit above.

## Phase 2 — per finding, in order

For each finding establish: (1) the exact input or environment that triggers it; (2) what happens instead of what should happen; (3) **reproduce it by running** — the sandbox has a shell, so run the offending fragment with the triggering value and cite the output; (4) rate by what it costs the user who hits it — a launcher that fails to start the runtime for a user whose home directory contains a space is High, not Low.

## Output

Produce a concise markdown report and nothing else. Do not modify any file. Output only the report.

Structure:
- A **Summary** section: exactly one sentence.
- A **Bugfixes** section: the findings, formatted as below. If nothing meaningful is found, write `No findings`.
- A **Risks / caveats** section.

Include only those three sections.

Begin each finding with a level-4 markdown heading containing only its Finding ID wrapped in backticks, on its own line:

    #### `CSCAN-<file-basename-without-extension>-<short-mnemonic>`

GitHub turns that heading into a stable `#cscan-…` anchor, so the finding can be linked from summaries and cross-scan indexes. Everything downstream — deduplication, validation, the fix sweep, the triage issue a maintainer reads — joins on this id. A finding written as a prose bullet without one is invisible to all of it, however good the analysis.

Immediately below the heading, write these fields on separate lines, in order:

- **Finding ID** — `CSCAN-<file-basename-without-extension>-<short-mnemonic>`. The mnemonic is a lowercase hyphenated descriptor of the defect's semantics (`CSCAN-startup-unquoted-home-path`, not `CSCAN-startup-finding-1`). Derive it from *what the bug is*, so a re-scan of the same file produces the same id for the same bug. Under 40 characters; no line numbers, version numbers, or anything that drifts.
- **Severity** — Critical / High / Medium / Low.
- **Confidence** — high / medium / low.
- **Location** — file:line and the function or clause name.
- **Class** — the Phase 1 class this belongs to, or `Unclassified (<short label>)` when it genuinely fits none.
- **Impact** — what it costs, in plain language, for someone who hits it (the topic threat note: which user, in which environment, sees which failure).
- **Evidence** — `verified` when you ran it and observed the behaviour (quote the command and the output), `asserted` when you reasoned about it only. A claim you could have tested but did not is `asserted`.
- **Suggested fix** — the smallest change that removes the defect.

Findings you considered and rejected go under a `### Ruled out` heading at the end, one bullet each with the reason. Do not give those a Finding ID.

### Ruling something out

A dismissal is the strongest claim in the report — "there is nothing here" — so it carries the heaviest burden of proof, not the lightest. A ruled-out entry whose basis is `asserted` does not stand: either verify it, or report the finding and let the validator decide. "I could not check this, so it is fine" is not a ruling. A false positive is caught downstream by the validator; a false negative is invisible, which is why the asymmetry runs this way.

Every claim of absence is a claim about a search space, and it stands only when the space and the search are named. Three shapes smuggle one in without naming it:

- A negative existence claim from a partial search. "This script never word-splits" quantifies over every expansion, not the ones you looked at. Name where you looked, or the basis is `asserted`.
- A parity claim without the upstream mechanism. "Matches the other launcher" asserts the absence of a difference. Name the mechanism and its default, not just the resemblance.
- A mitigation the threat model does not grant. "Only the local user can set this variable" asserts the attacker's absence past a door the threat model may hold open.

Write `No findings` in the Bugfixes section if nothing meaningful survives this bar.
````
